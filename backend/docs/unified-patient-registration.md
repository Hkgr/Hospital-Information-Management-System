# توحيد التسجيل وصلاحيات المهام

## نموذج البيانات وحدود الوصول

التسجيل الأساسي والعمل الطبي يستخدمان `DossierPersonalWriter` والهوية والكود والبطاقة والزيارة نفسها. لا توجد عملية نسخ أو دمج تلقائي للأسماء. البحث المحدود لا يعيد التاريخ الطبي أو العلاج أو المرفقات. فتح بطاقة مريض موجود في مشفى آخر يعيد استخدام هويته، ولا يمنح قراءة سياقه الطبي الآخر.

تاريخ فتح البطاقة مستقل عن تاريخ الزيارة الفعلي؛ لا يصح افتراض أن تاريخ إدخال البيانات هو تاريخ الزيارة. إعادة إرسال الحفظ تستخدم معرّف الطلب نفسه. الانتقال لاستكمال التسجيل يستخدم معرّف البطاقة والزيارة المحفوظين، ويظل إنشاء زيارة لاحقة فعلًا منفصلًا لبطاقة فعالة.

## جرد الصلاحيات وخريطة التوافق

المصدر التنفيذي للأسماء والنطاق والمتطلبات والبدائل القديمة هو `App\Services\Auth\TaskPermissions::TASKS`. تعاد هذه البيانات في `users/options` ضمن `permission_groups`. القيم في الأعمدة التالية أكواد تقنية للمشغّل، وليست نصوص دليل المستخدم.

| الصلاحية القديمة | المهام الجديدة | النطاق والأثر |
|---|---|---|
| `reception.view`، أو `dossiers.view` | `patients.basic.view` | عرض تعريف المريض في المشفى، دون التاريخ الطبي |
| `reception.patients.search`، أو `patients.search` | `patients.basic.search` | تفويض عالمي للبحث المحدود؛ لا تكفي إضافته لدور محلي |
| `reception.patients.create`، أو `patients.create` | `patients.basic.create` | تفويض عالمي لإنشاء الهوية، دون تعديل الهوية القائمة |
| `reception.register`، أو اجتماع `dossiers.create` و`dossiers.visits.create` | `patient_cards.register` | تسجيل بطاقة المشفى والزيارة الأولى؛ يحتاج عرض البيانات الأساسية وتفويض الهوية المناسب |
| `reception.correct` | `patients.own.correct` | لا تزال الملكية والمهلة والحالة والنسخة تمنع التصحيح غير المسموح |
| `reception.corrections.request` | `patients.corrections.request` | تقديم مقترح للمراجعة، دون اعتماده تلقائيًا |
| `dossiers.view` | `dossiers.medical.view` و`dossiers.visits.view` | قراءة السياق الطبي والزيارات؛ لا تُمنح لموظف التسجيل تلقائيًا |
| `dossiers.visits.update` | `dossiers.visits.draft.update` و`dossiers.diagnoses.update` | تعديل بيانات المسودة منفصل عن التشخيصات |
| `dossiers.visits.create` | يحتفظ بمعناه دون منح تعديل التشخيصات | يسمح بالتشخيصات في طلب إنشاء الزيارة نفسه فقط؛ تصحيح زيارة محفوظة يحتاج الصلاحية المفصلة |

| `dossiers.treatment.schedule` | `dossiers.treatment.schedule.create/update` | فصل إنشاء الموعد عن تصحيحه |
| `dossiers.treatment.correct` | `dossiers.treatment.administration.correct` و`dossiers.treatment.dispensing.correct` | لا تعني الوصفة إعطاءً أو صرفًا |
| `dossiers.treatment.void` | `dossiers.treatment.administration.void` و`dossiers.treatment.dispensing.void` | إلغاء موثق، مع بقاء قيود الحالة والنسخة؛ إلغاء الإعطاء المرتبط يحتاج أيضًا تعديل الموعد |
| `blood_bank.benefits.create/update` | `blood_bank.issue.create/update` و`blood_bank.transfusion.create/update` | فصل صرف المكوّن عن نقل الدم الفعلي، مع حفظ علاقة المرحلتين |
| `catalog.directory.update` | `catalog.directory.edit/deactivate/restore/reactivate` | تفويضات عالمية منفصلة؛ تغيير النشاط من نموذج التعديل يفحص صلاحية النشاط أيضًا |
| `catalog.directory.delete` | `catalog.directory.archive/destroy` | الأرشفة مستقلة عن الحذف النهائي، وقيود حماية المراجع باقية |
| `clinics.update` | `clinics.edit/deactivate/restore/reactivate` | ضمن المشفى |
| `clinics.delete` | `clinics.archive/destroy` | ضمن المشفى مع حماية التاريخ |
| `doctors.directory.update` | `doctors.directory.edit/deactivate/restore/reactivate` | تفويض عالمي مع استمرار عزل روابط المشفى |
| `doctors.directory.delete` | `doctors.directory.archive/destroy` | لا يتجاوز فحص المراجع |
| `stock.receive` | `stock.receipts.write/confirm` | إعداد المسودة منفصل عن تأكيد الرصيد |
| `stock.suppliers.manage` | `stock.suppliers.write` و`stock.stores.write` | فصل إدارة الموردين عن المستودعات |

الصلاحيات المفصولة بالفعل تبقى بأكوادها، ومنها: `dossiers.medical.update` و`personal.update` و`finalize` و`visits.complete`، صلاحيات المرفقات الأربع، `export/audit`، التشريح المرضي والتقييم والاستيراد، إنشاء الخطط واعتمادها وحالتها وتسجيل الإعطاء والصرف، التبرع وملف بنك الدم وتقاريره، المستفيدون وتدقيق الأدلة، روابط الأطباء، المستخدمون والأدوار، مراجعة التصحيح والتكرار، الإحصاء المجهل وإعدادات المشفى.

لم يُضف مسار تصحيح أو إلغاء زيارة مكتملة: التنفيذ الحالي يحمي الزيارة المكتملة من الكتابة، ولا توجد واجهة مستقلة مخولة لهذه الأفعال. كذلك توجد تعريفات مخزون قديمة للتسوية والإتلاف والمرتجع والتصدير دون مسارات فعلية في الإصدار الحالي؛ لا تُنشأ مهام جديدة توهم بأن هذه العمليات متاحة.

## آلية التوافق والإسناد

- التوافق أحادي الاتجاه: المنح القديم الفعال ينتج مهامه الدقيقة الفعالة داخل النطاق نفسه. المنح الدقيق لا ينتج الصلاحية القديمة ولا بقية المهام.
- لا يحدث توسيع بين الدور المحلي والتفويض العالمي، ولا تعاد تفعيل تعريفات معطلة.
- لا تتغير `role_permissions` أو تعيينات المستخدمين أثناء الترقية. وصول السوبر أدمن يبقى من آليته النظامية الحالية للصلاحيات الفعالة.
- قوالب التسجيل والإدخال الطبي والطبيب والمراجعة والإدارة اقتراحات يختارها المسؤول صراحة ويعدلها، ولا تُسند تلقائيًا لحساب قائم.
- لا يسمح الخادم بمنح صلاحية غير مملوكة. المتطلبات الناقصة للمهام الجديدة تعيد `ROLE_PREREQUISITES_REQUIRED`؛ لا تُضاف أثناء الحفظ بصمت.
- اختيار صلاحية عالمية في دور محلي وحده لا يفعّلها. يعرض إنشاء الحساب `pending_global_permissions` لجميع التفويضات العالمية المنتظرة. يراجعها مسؤول النظام عبر آلية التفويض القائمة.
- نقل دور قديم واسع إلى مهام أقل يحتاج مراجعة بشرية وإزالة المنح الواسع صراحة؛ لا يكفي إزالة مهمة دقيقة مع الإبقاء على بديلها القديم.

للإسناد: افتح «المستخدمون ← الأدوار والصلاحيات»، عاين مجموعة المهام، ثم أضف الاختيارات والمتطلبات المطلوبة صراحة واحفظ الدور. راجع جميع الحسابات المرتبطة بالدور قبل تعديله، لأن التعديل يخص الدور كله. إسناد الدور المحلي لحساب لا يُنشئ إسنادًا في `global_user_roles`. التفويض العالمي يبقى خطوة مشغّل مستقلة بعد مراجعة المستخدم والدور ومحتوى صلاحياته، وفق [دليل المرحلة الأولى](permissions-matrix-phase-one.md)؛ لا تشغّل أمر منح الأطباء لتفعيل التسجيل، ولا تُعد إسناد super_admin لحل نقص صلاحية موظف.

## الترقية والتراجع

### متطلب إلغاء إعطاء الجرعة

تتطلب `dossiers.treatment.administration.void` صلاحية `dossiers.treatment.schedule.update` إضافة إلى قراءة البطاقة والزيارات والعلاج: **الإلغاء يتضمن معالجة حالة الجلسة المرتبطة**، بإلغائها أو إعادة جدولتها وفق القواعد القائمة. يعرض وصف الصلاحية هذا السبب في محرر الأدوار، ويرفض حفظ دور جديد أو تعديل دور دقيق يفتقد المتطلب، دون إضافته تلقائيًا. يظل فحص الخادم داخل معاملة الإلغاء قائمًا، وقدرة `treatment_administration_void` في API لا تكون صحيحة إلا عند اكتمال الشرطين.

لا تحتاج هذه المعالجة migration أو تشغيل Seeder، ولا تغير أي تعيين قائم. الدور القديم الناقص يظل ناقصًا والإلغاء غير متاح له حتى يراجع مسؤول مخوّل الصلاحيات ويضيف المتطلب صراحة. إلغاء صرف الدواء عملية مستقلة ولا يكتسب هذا المتطلب.

اختبارا الانحدار الجديدان فشلا قبل الإصلاح (متطلب غير معلن وقدرة إلغاء معروضة رغم نقصه)، ثم نجحا بعده: 2 اختبار و54 تحققًا. يغطيان إنشاء الدور وتعديله وإعادة Seeder دون منح، ورفض الإلغاء عند نقص أي من الصلاحيتين، وعزل المنشأة ونسخ الواقعة والجلسة والخطة والحالة، والنجاح والتدقيق وإعادة الطلب. تُوثق نتائج إعادة تشغيل المجموعات الكاملة على SHA النهائي في PR #65.

```bash
php artisan test-db:check --connect --env=testing
php artisan test --env=testing --bootstrap=tests/Support/preserve-database.php --filter='TaskPermissionsTest|RoleApiTest|OncologyTreatmentTest|DossierCompletionTest|DossierCompletionSafetyTest|DossierWorkflowTest|PermissionMatrixTest|UserApiTest'
```

اختبارات الواجهة المتأثرة: `users.test.mjs` و`unified-registration-live.test.mjs` و`oncology-live.test.mjs`. المجموعتان الأخيرتان تستخدمان Next وLaravel وقاعدة الاختبار فعليًا. صُحح في اختبار الأورام خطآن نحويان سابقان في محددات النص، وأزيل كود المريض اليدوي المحظور حاليًا من بيانات التهيئة. يرسل الاختبار عيادة وطبيب التقرير المطلوبين حاليًا ويقبل عنوان Next محليًا فقط؛ لم يُغيّر التطبيق لتجاوز هذه الضوابط.

Migration إضافية: `2026_09_30_000002_define_task_permissions.php`. لا تعدّل المخطط الطبي أو migrations السابقة. تضيف تعريفات فقط باستخدام `insertOrIgnore` وتحافظ على التعريفات المعطلة والتعيينات. يمكن إعادة تثبيت التعريفات الناقصة بأمر مخصص، دون seeders عامة:

```bash
php artisan migrate --force
# اختياري لاستعادة تعريفات ناقصة، وليس لمنح أدوار أو مستخدمين:
php artisan db:seed --class=TaskPermissionsSeeder --force
```

هذه أوامر للمشغّل بعد مراجعة النشر؛ لم تُنفذ على الإنتاج. التراجع عن migration لا يحذف تعريفات قد تكون أُسندت وأصبحت جزءًا من تاريخ التفويض. عند التراجع عن التطبيق، تظل المهام الجديدة غير مستخدمة في النسخة القديمة؛ راجع الأدوار الدقيقة قبل التراجع حتى لا تفقد إمكانية العمل. لا تُنشأ تعيينات واسعة لتعويض ذلك تلقائيًا.

بعد نشر الواجهة يلزم بناء Next جديد، والتحقق بحساب تسجيل محدود وحساب طبي وحساب إداري؛ نجاح دخول المسؤول الشامل وحده لا يثبت صحة حدود الوصول.

## تحقق محلي

تستخدم الاختبارات MariaDB 10.11.18 محلية مع driver `mysql` وقاعدة `blood_bank_cities_testing` على `127.0.0.1:13416`. اجتاز `test-db:check --connect --env=testing`. bootstrap `tests/Support/preserve-database.php` يرفض قاعدة غير اختبارية أو ترقية معلقة، ويشغّل اختبارات المعاملات دون `migrate:fresh`.

طُبّقت migration الإضافية على القاعدة المأهولة دون إعادة تهيئتها. اختبر `TaskPermissionsTest` إعادة `up` مرتين و`down`، وبقاء الهوية والبطاقة والزيارات والتشخيصات والتدقيق وتعيينات الأدوار كما هي، وبقاء التعريف المعطل معطلًا.

شُغّلت المجموعة الوظيفية التالية:

```bash
php artisan test --env=testing --bootstrap=tests/Support/preserve-database.php --filter='TaskPermissionsTest|DoctorApiTest|ClinicApiTest|DirectoryLifecycleTest|CatalogApiTest|DossierCompletionTest|MedicationStockTest|RoleApiTest|PermissionMatrixTest|ReceptionReviewTest|DossierWorkflowTest|OncologyTreatmentTest|BloodEventsTest|DossierImportTest|DossierPathologyTest|ClinicalAdministrationTest|FacilityReportApiTest|DashboardApiTest|test_access_filters_deduplicates'
```

نتيجة المجموعة الأخيرة: 256 نجاحًا من 257، دون اختبارات متجاوزة؛ التعثر الوحيد كان طول كود منشأة في إعداد اختبار سياق الوصول، لا استجابة التطبيق. صُحح الإعداد ضمن طول العمود وأعيد الاختبار: نجاح واحد و163 تحققًا. نجحت الحالات الـ257 عبر التشغيلين؛ لم يُعد تشغيل المجموعة كاملة بعد تعديل هذا الإعداد. بلغ مجموع التحققات الناجحة 17559. أصلحت إعدادات قديمة كانت تفترض قاعدة خالية، وأكواد دليل يقبلها العميل، وغياب عيادة وطبيب في تقرير التشريح المرضي؛ لم تُغيّر بيانات القاعدة القديمة لتلبية هذه الافتراضات.

محاولة سابقة ضمّت `AuthApiTest` كاملًا أوقفت بقية التشغيل بواسطة حاجز حفظ القاعدة بعدما أعاد اختبار قديم تسمية جدول التدقيق (DDL ينهي معاملة MySQL). لم يُعطّل الحاجز ولم تُعد تهيئة القاعدة. لذا لا يُدّعى نجاح حزمة المصادقة كاملة أو كامل Laravel؛ أُعيد اختبار سياق الوصول المتأثر منفردًا بأسماء اختبار فريدة.

اختبارات الواجهة الحالية للأطباء والعيادات والأدلة والمخزون والمستخدمين وAppShell والدخول: 79 نجاحًا، صفر فشل، وتجاوز واحد معلن لاختبار دخول حي اختياري في الحزمة القديمة لعدم تهيئة متغيره. التكامل الجديد `frontend/tests/unified-registration-live.test.mjs` يستخدم خادمي Next standalone وLaravel فعليين وقاعدة الاختبار؛ يفحص ترويسة الخادم الاختباري ولا يستخدم اعتراض API. التهيئة تضيف بيانات تدريب فقط، والتنظيف يبطل رموز حساباتها ويعطلها دون حذف تاريخها.

نجح TypeScript وproduction build وPint على ملفات PHP المتأثرة و`git diff --check`. فحص lint لكل TS/TSX المتأثرة أظهر خطأ سابقًا واحدًا في `OncologyPanel.tsx:34` (`set-state-in-effect`) وتحذيرين سابقين، في أسطر مطابقة لـdevelop. باستثناء هذا الملف السابق التعثر: صفر أخطاء وتحذير سابق واحد في `DossierScreen`. لم تُغير آلية اختيار موعد الجرعة لمجرد إخفاء نتيجة lint.

التكامل الحقيقي النهائي نجح في تشغيل واحد: 8 حالات، صفر فشل أو تجاوز، خلال 76.37 ثانية، بعد بناء Next جديد. يشمل التسجيل والتحقق وحفظ المسودة وتسليم السجل نفسه، منع الوصول الطبي لموظف التسجيل، تنبيه التكرار، المهام السريرية الدقيقة، متطلبات الأدوار ومنع التصعيد، والدليل والنماذج ولوحة المفاتيح عند 390 و768 و1440px. هذه نتيجة مستقلة عن اختبارات الواجهة الـ79 التي تستخدم محاكاة API.

لم يُختبر شيء على قاعدة المشفى أو الإنتاج، ولم تُستخدم SQLite. راجع [اللقطات الفعلية](../../frontend/docs/unified-registration-review.md) من التكامل النهائي.
