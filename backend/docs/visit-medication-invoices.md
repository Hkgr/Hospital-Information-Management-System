# فواتير الأدوية داخل بطاقة المريض

يدعم كل نوع حالي (`unlinked` و`dose_linked` و`outside`) عدة فواتير مستقلة في الزيارة نفسها. هذه سجلات الوصفات الحالية وليست نظامًا محاسبيًا، ولا تكتب في `visit_medications` ولا تسجل صرفًا أو إعطاءً تلقائيًا. تبقى نتيجة الزيارة مستقلة.

## الإدخال والحفظ

«إضافة فاتورة» يبقى متاحًا بعد الأولى. اختر الفاتورة من أزرارها قبل تعديل الطبيب والعيادة والتاريخ والأدوية والملاحظات والتمويل/سبب عدم التوفر. الحفظ يرسل **الفاتورة المختارة فقط**؛ لا يرسل مسودات الفواتير الأخرى، ولا يمحوها أو يمحو تبويبًا آخر. المسودات غير المحفوظة تبقى داخل الصفحة، وليست حفظًا تلقائيًا دائمًا. احفظ كل مسودة قبل إغلاق الصفحة. يعاد تحميل جميع الفواتير المحفوظة بمعرفاتها وأدوية كل فاتورة.

يبقى عقد `PUT /api/dossiers/{dossier}/visits/{visit}/medications` متوافقًا: `prescription` واحدة أو `null` و`outcome` واحدة أو `null`، و`request_id` ونسخة الزيارة. تعديل سجل محفوظ يتطلب معرفه ونسخته، وكذلك نسخ أدويةه؛ الحذف صريح وذو سبب. ما لم يُرسل يبقى كما هو. القراءة تعيد جميع `clinical.prescriptions`؛ الحقل المفرد القديم يبقى للتوافق ولا تستخدمه الواجهة لإخفاء الفواتير الإضافية. التعارض يعرض الفواتير حسب معرفاتها دون تحويل فاتورة جديدة إلى فاتورة قديمة من النوع نفسه.

## التمويل

كان النموذج يقرأ التمويل من خيارات العلاج التي تتطلب `dossiers.treatment.view`، وكان يخفي فشل التحميل كقائمة فارغة. الآن `GET /api/dossiers/prescription-funding?facility_id=...` يتحقق من `dossiers.visits.view` و`dossiers.prescriptions.update` في المشفى، ويعيد مصادر التمويل الفعالة فقط. تظهر حالات التحميل والفشل وإعادة المحاولة وغياب المصادر، مع الاحتفاظ بالاختيار التاريخي ومسودة الفاتورة.

جدول `funding_sources` فارغ في ملف SQL المرجعي؛ لا تكفي إضافة مصدر اختبار. اعتمد المستخدم خيارات مصدر الدواء العام الموجودة في `OncologyQueries::MEDICATION_SOURCES`: وزارة الصحة، مؤسسة الرواد، جهة أخرى، نفقة شخصية، ولا يوجد. تُستخدم الرموز والأسماء نفسها، دون اختراع جهات أو استيراد SQL. لا يستطيع مدخل البيانات إنشاء تعريفات التمويل أو الأدوية. التمويل إلزامي للفواتير المرتبطة بالجرعة؛ الأنواع الأخرى تحافظ على قواعدها السابقة.

## التفعيل بعد نشر النسخة المراجعة

هذه تعليمات للمشغّل؛ لم تُنفّذ على الإنتاج. بعد النسخة الاحتياطية ومراجعة بيئة التشغيل، طبّق الترحيل الإضافي المحدد فقط:

```bash
php artisan migrate --path=database/migrations/2026_10_12_000001_allow_multiple_visit_prescriptions_per_kind.php --pretend
php artisan migrate --path=database/migrations/2026_10_12_000001_allow_multiple_visit_prescriptions_per_kind.php --force
php artisan dossiers:setup-prescription-funding
```

الترحيل يزيل فهرس التفرد `prescriptions_one_kind` فقط. لا يغيّر المعرفات أو أدوية الفواتير أو روابط المنشأة أو قيود النوع. يحتفظ بالعمود المولد لتوافق التراجع. `down` يفشل قبل الكتابة إذا كانت هناك عدة فواتير فعالة من النوع نفسه، ولا يحذف أو يلغي فاتورة كي يعيد القيد. لا تعدّل migration قديمة أو تسجّلها يدويًا.

راجع ADD / KEEP / KEEP DISABLED ثم طبّق المصادر المعتمدة الناقصة بمشفى حقيقي ومرجع للمشغّل:

```bash
php artisan dossiers:setup-prescription-funding --apply --facility=ACTUAL_FACILITY_ID --execution-reference=CHANGE_REFERENCE_AND_OPERATOR
php artisan dossiers:setup-prescription-funding
```

يحفظ الأمر السجلات الحالية ومعرفاتها وأسمائها وحالتها، ويعيد استخدام الاسم المطابق حتى لو كان رمزه تاريخيًا. لا يعيد تفعيل مصدر معطل ولا يضيف بديلًا له. يرفض المطابقة الملتبسة قبل أي كتابة. إعادة التنفيذ لا تضيف تعريفات أو تدقيقًا مكررًا. التدقيق بأثر إنشاء فقط، `actor_id=NULL` لأمر الطرفية ومرجع التنفيذ محفوظ؛ لا يُنسب للمستفيد. لا Seeders عامة ولا تعديل للأدوار عبر هذا الأمر.

أعد بناء Next بإعداد `LARAVEL_API_URL` الصحيح لأن التحويل الجديد محدد أثناء البناء، وانشر ناتج standalone الجديد بالطريقة الحالية. لا يكفي إعادة تشغيل بناء قديم. أمر تصحيح دور `data_entry` من [دليل الصلاحيات](data-entry-card-permissions.md) يبقى كما هو، ولا يلزم تفويض عالمي جديد أو منح صلاحيات دليل لتسجيل الفواتير.

## التحقق

اختبار الانحدار قبل الإصلاح رفض الفاتورة الثانية بـ409، وتمثيل المسودة القديم احتفظ بمعرف الفاتورة الثالثة وحده. تغطي الاختبارات الجديدة ثلاث فواتير من نوع واحد، استقلال التمويل والأدوية، إعادة الطلب، إعادة القراءة، تعديل واحدة، مسودات غير مرسلة، التوافق القديم، وسحب الصلاحية وعزل المشفى. يتضمن التحقق الفعلي بناء Next جديدًا وLaravel وMariaDB اختبارية، ببيانات اصطناعية ومصادر التمويل المعتمدة. اختبار فشل/فراغ التحميل في المتصفح حقن أعطال للواجهة فقط؛ يُذكر منفصلًا عن التكامل الفعلي. توجد أيضًا حالة قائمة فارغة فعلية في اختبار Laravel داخل معاملة تتراجع.

`tests/Support/verify-multiple-prescription-migration.php` مخصص حصريًا لقاعدة اختبار معزولة مأهولة بعد حاجز الأمان. يقارن جميع قيم ومعرفات الرؤوس والبنود خلال التراجع والترقية، ثم يثبت منع التراجع عند تعدد الفواتير دون تغيير البيانات. لا يستعمل fresh/reset أو بيانات المشفى. نتائج التشغيل الفعلية موثقة في PR.
