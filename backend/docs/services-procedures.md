# إدارة الخدمات والإجراءات

## سياق المنشأة المشترك — إصلاح ما بعد PR #13

لا يحتاج فتح القسم إلى `CATALOG_FACILITY_CODE`؛ أُزيل ملف إعداد catalog والقيمة النموذجية. غياب المتغير أو بقاء قيمة قديمة فيه لا يؤثر على اختيار المنشأة. لا يلزم إضافة إعداد خاص بالخدمات عند نشر هذا الإصلاح، ولم تُعدّل إعدادات الإنتاج.

المرجع الفعلي للأطباء والعيادات هو `access` في بيانات المستخدم الحالي، وليس سياقًا مركزيًا في AppShell. روابط القائمة الجانبية تدخل الأقسام دون `facility_id`: تُرشح المنشآت بصلاحية عرض القسم ثم تُختار الأولى بترتيب الهوية القادم من Laravel (`facilities.code` ثم `id`). إذا حمل الرابط `facility_id` فهو مقدّم على الافتراضي، ولا يُستبدل بمنشأة أخرى عند غياب الوصول. تستخدم الخدمات `catalog.view` وحدها لهذا القرار؛ امتلاك `doctors.view` أو `clinics.view` لا يمنح وصولًا إليها.

استُخرج الجزء المتكرر إلى `directoryFacility` وأعيد استخدامه في الأقسام الثلاثة. يوجد فرق قديم محدود: العيادات تعامل `facility_id=` الفارغ كغياب المعامل، والأطباء يرفضونه. حُفظ سلوك المرجعين كما هو، واتُّبع سلوك الأطباء الصريح في الخدمات. لا توجد قائمة اختيار منشآت في الخدمات؛ يُعرض اسم المنشأة المختارة وتستمر الروابط والطلبات بحمل معرّفها.

يبقى `GET /api/service-catalog/context?facility_id=...` للتحقق من النشاط وصلاحية `catalog.view` الحالية في الخادم قبل فتح مساحة القسم. يعيد `data.facility` المحدودة نفسها، و403 بلا بيانات منشأة عند الرفض، و422 للمعرّف الغائب أو غير الصالح في API. تعرض الصفحة رسالة عن تعذّر تحديد المشفى أو التحقق من الوصول إليه، لا رسالة حقول نموذج. بقي تحويل Next المحدد للمسار كما هو وهو يمرر query parameters؛ عُدّث OpenAPI ليُلزم `facility_id` ويلغي خطأ إعداد الرمز. جميع طلبات البيانات تواصل الفحص المستقل للصلاحيات والنشاط.

تغيير المنشأة يفصل مساحة العمل ويُلغي الطلبات القديمة؛ لا تُعرض النتائج السابقة أثناء التحقق من سياق جديد، ولا تعيد استجابة متأخرة تفعيل السياق السابق. لا تغيير لمنطق الفئات والمسودات والبحث والوقائع والتصدير أو دورة الحياة.

## البحث عن المستفيدين بالاسم الكامل

يدعم `search` في `/api/service-catalog/{kind}/{item}/events` الاسم الأول واسم العائلة والاسم الكامل الظاهر في الجدول وكود المريض. تُوحّد المسافات المتكررة في عبارة البحث، بما فيها tab وUnicode whitespace، وتُهمل المسافات الخارجية. تُطابق كذلك الأسماء المركبة المخزنة بمسافات زائدة دون تعديل بيانات المريض أو طريقة عرض اسمه.

تُمرر قيمة `LIKE` بمعامل مربوط، وتبقى `%` و`_` و`\` حرفية داخل العبارة. يظل البحث في MySQL وقبل حساب الصفوف والإجماليات والترقيم، مع شروط المنشأة والأهلية والتاريخ والصلاحيات نفسها. تُحسب الوقائع الصحيحة المتكررة منفصلة، والمريض مرة واحدة في `unique_patients`. لا تغيّر في الواجهة أو خيارات البحث أو تصميم الجدول.

**إعداد التشغيل الحالي:** يتبع القسم سياق الهوية والرابط الموثق أعلاه؛ لا إعداد رمز مشفى خاص بالخدمات.

اختبارات الانحدار: `CatalogBeneficiarySearchTest` للخدمات والإجراءات على MySQL الاختبارية بعد `php artisan test-db:check --connect --env=testing`، واختبارا المتصفح الحيان بواسطة `node --test --test-name-pattern='full beneficiary name' tests/catalog-live.test.mjs` عبر Next standalone ثم Laravel ثم MySQL، دون محاكاة API. لا تُشغّل اختبارات `RefreshDatabase` بالتزامن مع fixture الحية.

نتائج هذا الإصلاح: فشل اختبارا الخادم قبل تعديل المنطق لأن البحث بالاسم الكامل أعاد صفرًا بدل تقديمين، وفشل اختبارا المتصفح للنوعين. بعد الإصلاح نجح `php artisan test --env=testing --filter='CatalogBeneficiarySearchTest|CatalogWorkflowTest|CatalogApiTest'` (15 اختبارًا، 1215 تحققًا)، ونجح اختبارا المتصفح الحيان. اجتازت قاعدة `hospital_testing` على `mysql` في `127.0.0.1:13306` حاجز الأمان والاتصال. نجحت فحوص Pint وESLint لملف الاختبار و`git diff --check`. استُخدم بناء Next standalone الحالي؛ لم يتغير كود الواجهة أو إعداد بنائها في هذا الإصلاح، ولم تُعَد فحوص البناء العامة.

## تحديث سياق المشفى والفئات ووقائع التقديم

في إصلاح `fix/catalog-workflows-and-consistency` اللاحق لدمج PR #12:

- استُبدل لاحقًا تحديد المشفى بالرمز الإلزامي بسياق الهوية والرابط المشترك الموثق أعلاه. يبقى `context` للتحقق من `facility_id` المختار، وجميع مسارات البيانات تستمر بالتحقق منه في الخادم.
- `POST /api/service-catalog/categories`: `facility_id`, `code` (50), `name_ar` (200), `is_active` (boolean). يلزم **`catalog.directory.create` عالميًا** مع وصول المنشأة؛ المنح المحلي وحده لا يكفي. ينشئ الحقول الموجودة في `service_categories` ويسجل التدقيق داخل transaction؛ يعيد 201 مع `id/code/name_ar/is_active`. تكرار الرمز وفق MySQL يرجع 422 عربيًا بجانب `code`. لا صلاحية أو migration جديدة، ولا إسناد تلقائي لأي دور. الفئات غير الفعالة محفوظة وتُستبعد من الخيارات الجديدة.
- يعيد السجل `classification_name_ar` لعرض فئة الخدمة/نوع الإجراء حتى لو عُطل التصنيف لاحقًا، دون تغيّر صلاحية اختياره لتعريف جديد.
- `GET /api/service-catalog/{kind}/{item}/events` يحتاج `catalog.beneficiaries` في المنشأة. يعيد `data[]` بحقوق `key`, `source`, `event_id`, `patient_code`, `patient_name`, `performed_on`, `visit_no`، مع `meta` المعتاد و`totals.unique_patients/presentations`. `key` هو `source:event_id`؛ المصادر `visit_service`, `visit_procedure`, `blood_procedure`. كل واقعة صحيحة تبقى صفًا مستقلاً حتى لنفس المريض. الربط بمعرّفات الجداول لا يضاعف الواقعة، وتبقى إحصاءات المستفيدين `COUNT(DISTINCT patient_id)`.
- مرشحات الوقائع: `search` باسم المريض/كوده، `from/to` شاملان بتاريخ `performed_on`، `sort=performed_on|patient_code|patient_name|visit_no` و`direction=asc|desc`، `page` و`per_page=10|20|50|100`. الافتراضي تاريخ التقديم تنازليًا، ثم المصدر والمعرّف لضمان ترتيب ثابت. العدّان من جميع النتائج المطابقة داخل transaction، وليس من الصفحة المعروضة. لا جلب كامل للمرضى في المتصفح ولا رابط ملف مريض وهمي.
- بقيت أهلية الزيارة `complete` وغير ملغاة، وتواريخ المنشأة، وقواعد أحداث متلقي الدم المعروف كما هي. التاريخ من الحدث، دون استبداله بـ`created_at` أو تاريخ الزيارة. الحدث بلا تاريخ لا يدخل معيار الأهلية الحالي؛ لدى الواجهة وصف صريح إذا وصل تاريخ غير متوفر، دون اختلاق قيمة.
- أُضيفت تحويلات Next المحددة للمسارات الثلاثة، مع عقود OpenAPI. بقي Bearer Sanctum بقدرة `api` والحساب الفعال و`private, no-store` والحفظ بالنسخة والتاريخ والتقارير كما هي.

نتائج الإصلاح والمكوّنات المشتركة والمقارنة المرئية وأوامر تشغيل التكامل موثقة في [مراجعة الواجهة](../../frontend/docs/catalog-consistency.md). نتائج الأقسام اللاحقة أدناه توثق التنفيذ الأصلي؛ النتائج الأحدث: Laravel **14 اختبارًا/1016 تحققًا**، واجهة الخدمات **14**، واجهات الأطباء والعيادات **40**، والتكامل الحقيقي **7**. MySQL الاختبارية `hospital_testing` على `127.0.0.1:13306` بعد اجتياز الحاجز. لا اتصال بالإنتاج ولا استخدام SQLite. لا تشغّل الاختبارات ذات `RefreshDatabase` بالتزامن مع fixture الحية.

تعريفات الدليل في جدولي `services` و`procedures` الحاليين مشتركة بين المنشآت؛ تقديم تعريف لمريض حدث علاجي مستقل. الهوية `(kind, id)`، ولا توجد علاقة خدمة ← إجراء أو ارتباط تعريف مباشر بالعيادات في المخطط الحالي. لذلك لا تنشئ الوحدة جداول موازية أو علاقات افتراضية. لا تشمل الفوترة أو التسعير أو المخزون أو إدخال الأحداث العلاجية.

## المخطط والكتابة

Migration: `2026_09_13_000001_add_catalog_management_fields.php` تضيف إلى كلا الجدولين `description` و`lock_version` (افتراضي 1) و`archived_at` مع فهرس. لا تعدل migrations الأصلية. التراجع يزيل الحقول الجديدة فقط، ولذلك يفقد أوصاف الوحدة وحالة أرشفتها إن استُخدم لاحقًا.

الكود يدوي، مطلوب حتى 50 محرفًا، وفريد داخل النوع وفق collation وقيود MySQL الحالية، بما فيها التعريفات المؤرشفة. يجوز تساوي كود خدمة وإجراء. قيد unique يحسم السباق وتتحول مخالفة 1062 إلى خطأ حقل `code` (422). الاسم العربي مطلوب حتى 200، الوصف اختياري حتى 10000، والحالة boolean مطلوبة. الخدمة تحتاج `category_id` من `service_categories`، والإجراء يقبل `procedure_type_id` اختياريًا من `procedure_types`. الاختيارات الجديدة فعالة فقط؛ يمكن الاحتفاظ بالتصنيف الحالي إذا تعطّل لاحقًا. لا توجد إدارة تصنيفات جديدة في هذه المهمة.

النوع ثابت دائمًا؛ التعديل يستهدف الجدول الأصلي دون نقل التاريخ. لا يتغير `name_en` أو إعدادات `allow_external`/`requires_specialist` أو ترتيب التعريفات الخفي. الكتابة داخل transaction مع قفل السجل وفحص `lock_version` وتسجيل audit؛ كل كتابة ناجحة تزيد النسخة. 409 لا يعاد حفظه تلقائيًا. الواجهة تحتفظ بالمسودة، تجلب النسخة الحديثة عند طلب المستخدم، تعرض مقارنة حقول، وتحتفظ بقيم النسخة الحديثة افتراضيًا حتى يختار المستخدم حقول مسودته ويؤكد حفظًا مستقلًا. الإغلاق وتغيير المنشأة يلغي طلبات النافذة.

التعطيل/إعادة التفعيل لا يغير التاريخ. الأرشفة تجعل التعريف غير فعال، والاستعادة تبقيه غير فعال حتى إعادة تفعيل مستقلة. معاينة الحذف تفحص المراجع؛ ويعاد الفحص داخل معاملة الحذف. الحذف محظور عند أي مرجع، حتى ملغى: `visit_services` للخدمات؛ `visit_procedures` و`blood_recipient_procedures` للإجراءات؛ و`report_metric_catalog_items` لكليهما. FK يمنع مرجعًا متزامنًا متأخرًا. لا تحذف الأرشفة أي حدث أو تعيد فتحه. `/options` يستبعد المعطل والمؤرشف دائمًا. لا توجد APIs لتسجيل تقديم العلاج حاليًا؛ يلزم أن يستخدم أي مستهلك مستقبلي هذه الاختيارات ويعيد فحص أهلية التعريف عند كتابة الحدث، ضمن مهمة تقديم العلاج.

## الصلاحيات ونطاق المنشأة

Laravel وSanctum مسؤولان عن المصادقة. جميع المسارات تستخدم Bearer بقدرة `api`، حسابًا فعالًا، والاستجابات `private, no-store` بما فيها الأخطاء. FastAPI لم تتغير. اتبعنا خدمات التحقق من الصلاحيات الديناميكية المعتمدة للأطباء والعيادات (`CatalogAccess`) دون نظام صلاحيات موازٍ.

`facility_id` مطلوب في كل طلب، ويُفحص الوصول للمنشأة الفعالة قبل قراءة العنصر أو مرضاه. تعريفات الدليل عالمية بطبيعتها؛ هوية المرضى والأعداد والتاريخ والتقارير تخص المنشأة المحددة فقط. لا تمنح صلاحية قراءة الدليل وصولًا إلى أسماء المرضى.

| الصلاحية | النطاق والاستخدام |
| --- | --- |
| `catalog.view` | دور منشأة: الدخول والقائمة والتفاصيل والاختيارات |
| `catalog.export` | دور منشأة، بالإضافة إلى view: Excel/PDF |
| `catalog.beneficiaries` | دور منشأة، بالإضافة إلى view: هوية المستفيدين الأساسية |
| `catalog.audit` | دور منشأة، بالإضافة إلى view: سجل التغييرات في هذه المنشأة |
| `catalog.directory.create` | دور عالمي صريح: إضافة تعريف مشترك |
| `catalog.directory.update` | دور عالمي صريح: تعديل وتعطيل واستعادة وإعادة تفعيل |
| `catalog.directory.delete` | دور عالمي صريح: معاينة حذف وحذف نهائي وأرشفة |

تشغيل `CatalogPermissionsSeeder` يضيف تعريفات الصلاحيات فقط باستخدام `insertOrIgnore`؛ لا يمنح أدوارًا ولا يعيد تفعيل صلاحية معطلة. ليس مضافًا تلقائيًا إلى DatabaseSeeder. بعد مراجعة مسؤول الصلاحيات، تُربط الصلاحيات بدور عبر `role_permissions`، ثم يربط الدور بالمستخدم والمنشأة عبر `facility_user_roles` للصلاحيات المحلية، وبالمستخدم عبر `global_user_roles` للكتابة العالمية. يحتاج الكاتب كذلك `catalog.view` في منشأة يحق له العمل فيها. وضع صلاحية directory في دور منشأة وحده لا يجيز تعديل الدليل المشترك. لا يستنتج التفويض من اسم ADMIN ولا يُمنح لحسابات موجودة آليًا.

## تعريف المستفيدين

تستخدم القائمة والتفاصيل والنافذة والتصدير العلاقة SQL نفسها من `CatalogBeneficiaries::facts`:

- خدمة: `visit_services → visits`، والإجراء: `visit_procedures → visits`. يطابق الحدث والزيارة المنشأة؛ حالة الزيارة النصية `complete`، دون `voided_at` في الحدث أو الزيارة، و`performed_on` لا يتجاوز تاريخ اليوم بمنطقة المنشأة.
- إجراء أيضًا: `blood_recipient_procedures → blood_transfusions`، ضمن المنشأة، نقل غير ملغى، مريض معروف، وتاريخا التنفيذ والنقل لا يتجاوزان اليوم. إذا ارتبط النقل بزيارة، يجب أن تكون مكتملة وغير ملغاة ومطابقة للمريض والمنشأة.
- تجمع المصادر بـ UNION ثم يحسب `COUNT(DISTINCT patient_id)` لكل `(kind, item_id)`؛ المريض المتكرر أو المشترك بين المصدرين يحسب مرة واحدة للعنصر، ومرة مستقلة لكل عنصر آخر استفاد منه. لا يستخدم عدد الزيارات أو الكميات.
- الصفر يعني وجود مصدر موثوق دون مستفيدين مؤهلين. مستلم الدم الخارجي دون `patient_id` لا يمكن اعتباره مريضًا فريدًا مسجلًا؛ يُستبعد من هذا العدد، ولا يُنشأ له مريض مصطنع.

نافذة المستفيدين لا تحمل المرضى مسبقًا، وتعرض `id, patient_code, first_name, family_name` فقط، مع بحث وتقسيم صفحات من الخادم. لا توجد صفحة سجل مريض منفذة في المشروع، ولذلك تعرض الواجهة هذا القيد دون رابط وهمي.

فحص EXPLAIN على البيانات الاصطناعية أظهر استخدام فهرس الزيارات الموجود حسب المنشأة، وفهارس الأحداث حسب الزيارة، وPK لنقل الدم والزيارة المرتبطة؛ استخدم فرع أحداث الدم فهرسًا مغطّيًا في العينة الصغيرة. التجميع وUNION يتطلبان جدولًا مؤقتًا وترتيبًا، والبحث الجزئي ليس بحثًا مفهرسًا بالكامل. عدد استعلامات القائمة ثابت عند زيادة التعريفات من 4 إلى 34. لم تضف فهارس تخمينية إلى الأحداث؛ هذه ليست نتيجة اختبار تحميل بحجم إنتاجي، ويجب إعادة قياس الخطة بالحجم الفعلي قبل قرار تحسين إضافي.

## عقد API وNext

الأساس `/api/service-catalog` في Laravel، و`/hospital-api/service-catalog` من المتصفح. صفحة الواجهة `/services-procedures` والتفاصيل `/services-procedures/{kind}/{id}`. التحويلات محددة في next.config.ts، تستعمل `LARAVEL_API_URL` ومعرّفات رقمية ونوعي service/procedure فقط، ولا تفتح proxy عامًا.

| الطريقة واللاحقة | الوظيفة |
| --- | --- |
| GET / POST على الأساس | قائمة / إنشاء |
| GET `/classifications` | فئات الخدمات وأنواع الإجراءات الفعالة |
| GET `/options` | تعريفات مؤهلة للاختيار الجديد |
| GET `/export/{xlsx\|pdf}` | جميع النتائج المطابقة، والأعمدة المختارة |
| GET / PUT / DELETE `/{kind}/{item}` | تفاصيل / تعديل / حذف |
| GET `/{kind}/{item}/deletion-preview` | قرار delete أو archive والموانع والنسخة |
| POST `/{kind}/{item}/{archive\|restore\|deactivate\|reactivate}` | دورة الحياة، مع lock_version |
| GET `/{kind}/{item}/beneficiaries` | المرضى الفريدون |
| GET `/{kind}/{item}/history` | audit في المنشأة، بأحدث حدث أولًا |
| GET `/{kind}/{item}/report` | PDF تفاصيل مستقل عن جاهزية جدول القائمة |

مثال إنشاء خدمة:

```json
{"facility_id":1,"kind":"service","code":"SRV-001","name_ar":"خدمة","description":"وصف","is_active":true,"category_id":1}
```

الإنشاء 201 والتعديل/التفاصيل 200 داخل `data`؛ العنصر: `id, kind, code, name_ar, description, category_id, procedure_type_id, is_active, archived_at, lock_version, patient_count, patient_count_definition`. القائمة `{data: [...], meta: {page, per_page, total, last_page}, capabilities: {...}}`؛ التفاصيل تتضمن capabilities أيضًا. التعديل يرسل الحقول كاملة دون kind ومع lock_version. الحذف 204 بلا محتوى. أخطاء المجال `{error:{code,message}}`، والتحقق 422 `{message, errors}`. تشمل الحالات 401، 403، 404، 409 و500 الآمنة دون SQL أو stack trace. OpenAPI التفاعلي الحالي `/docs/api` و`/docs/api.json` يوثق المسارات والعقود والصلاحيات وتعريف الإحصاء، مع فصل schema الإنشاء عن التعديل.

القائمة تدعم `search` حتى 200 بالاسم والكود، `kind=service|procedure`، `status=active|inactive|archived` (الافتراضي غير المؤرشف)، `sort=code|name_ar|kind|is_active|patient_count`، `direction=asc|desc`، `page` و`per_page=10|20|50|100`. الترتيب ثابت بمفاتيح النوع والمعرف عند التساوي. `columns[]` يختار من number/code/name_ar/kind/description/patient_count/is_active. التصدير يتجاهل ترقيم الصفحة فقط ويشمل جميع المطابقات، حتى 1000؛ ما فوقها 422 دون اقتطاع صامت. يستعمل renderer Cairo الحالي ويحافظ على الأكواد كنص والعدادات كأرقام في XLSX. رقم التقرير ببادئة SP؛ تقارير الأطباء والعيادات دون تغيير.

الواجهة تحتفظ بالنتائج السابقة أثناء تحديث السياق نفسه مع توضيح أنها سابقة؛ التصدير محظور أثناء debounce، انتظار أحدث طلب، فشله أو revision بعد الحفظ. الحارس موجود داخل دالة التصدير أيضًا. تتبع الجاهزية هوية الطلب/مراجعته عبر hook الدليل الحالي، ويُلغى القديم عند تغير البحث أو المنشأة/الجلسة. تعود الفلاتر مع URL وتنقل التفاصيل.

## إعداد وتشغيل التحقق المحلي

استخدم `.env.testing` غير المتتبعة، وفق `.env.testing.example` وحاجز `TestDatabaseSafety`: testing + mysql + قاعدة تنتهي `_testing` أو تبدأ `test_`، مع تأكيد صريح للمضيف والقاعدة. لا تستخدم قاعدة تطوير أو إنتاج، ولا SQLite، ولا تشغل live suite بالتزامن مع RefreshDatabase.

```sh
# backend؛ بعد تجهيز قاعدة اختبار معزولة ومصرح بها
php artisan test-db:check --connect --env=testing
php artisan migrate --env=testing
php artisan db:seed --class=CatalogPermissionsSeeder --env=testing
php artisan test --env=testing --filter='CatalogApiTest|ClinicApiTest|DoctorApiTest|DirectoryReportTest'
php vendor/bin/pint --dirty --test
# خادم Laravel للاختبار الحي؛ APP_ENV=testing
php -S 127.0.0.1:8005 tests/Support/directory-routing-server.php
```

في frontend اضبط `LARAVEL_API_URL=http://127.0.0.1:8005/api` وقت `npm run build`. انسخ public و.next/static إلى .next/standalone بالشكل المعتاد، ثم شغّل `.next/standalone/server.js` مع `PORT=3105` و`HOSTNAME=127.0.0.1`. الاختبارات تستخدم Chrome المثبت محليًا. اختبارات AppShell تحتاج أيضًا `PLAYWRIGHT_CHANNEL=chrome` و`TEST_BASE_URL=http://127.0.0.1:3105`.

```sh
npm run test:catalog
npm run test:catalog-live
npm run test:shell
npx tsc --noEmit
npm run lint
npm run build
git diff --check
```

`catalog-live.php` يعيد فحص الحاجز قبل توليد البيانات الاصطناعية، ويحفظ التوكنات مؤقتًا في storage/framework/testing المحجوب عن Git. suite الحية لا تستخدم page.route أو استجابات API محاكية: جميع HTTP تمر بـ Next ثم Laravel ثم MySQL، والمتصفح ينشئ كلا النوعين ويستعرض المرضى والتفاصيل والسجل. ينهي الاختبار بإبطال توكناته وحذف ملفها؛ يحتفظ بالسجلات الاصطناعية للمراجعة في قاعدة الاختبار. صور المراجعة وEXPLAIN تبقى محلية غير متتبعة، ولا توجد بيانات دخول أو ملفات تقارير في Git.
