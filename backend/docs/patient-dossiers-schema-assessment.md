# Patient dossiers — Phase 1 schema assessment

Assessed before implementation against develop `9f14022` (including merged PR #19). Migrations are deployed history; no production connection or inference from live patient data was used. Application queries checked: CatalogBeneficiaries, BloodEventQueries/Writer, DirectoryReferences, UserAccessContext and the existing API routes.

| Existing structure | Verified meaning / Phase 1 reuse |
| --- | --- |
| `patients` (`2026_09_09_000003`) | Global person identity; unique patient_code, names, birth date/accuracy, gender, phones, governorate/city FKs, address/displacement, administrative identity fields, created_by and lock_version. Read current personal fields through patient_id; never copy them into a dossier. |
| `patients.paper_file_number`, first_known_visit_date, created_at | Paper reference is nullable, nonunique and not facility scoped; neither timestamp proves dossier opening. No automatic mapping or backfill. Operational review must reconcile legacy references explicitly. |
| `patient_identifiers`, patient_disabilities, patient_search_tokens | Identifier uniqueness and structured documented disabilities/search tokens. Disability types with documented_on are not the requested free-text dossier disability/history fields; keep both meanings separate. Existing token maintenance is not an established dossier search pipeline. |
| `facilities`, users, roles, permissions, role_permissions, facility_user_roles | Active-facility and active-role/permission joins in UserAccessContext are authoritative. Global role assignments added by the doctor migration do not imply dossier access. No existing seeded permission accurately grants dossier reading. |
| `visits` (`000004`) | Global visit_no; explicit patient_id + facility_id; actual visit_date, status, void markers, entered_by/updated_by, lock_version, required reporting period. Existing composite keys `(id,facility_id)` and `(id,patient_id)`. No dossier link. Add a nullable explicit link; do not assign existing visits merely because their patient matches. |
| visits.clinic_id / attending_staff_id / resident_staff_id | Clinic FK includes facility; staff IDs reference staff. These are visit-level associations, not evidence of a clinic for every diagnosis. Show legacy visit-level context separately without attributing it to diagnoses. |
| `visit_diagnoses` → diagnoses / diagnosing_staff_id | Composite visit/facility FK and explicit diagnosing doctor; diagnosed_on currently required; is_primary exists historically but is ignored in the dossier. No per-diagnosis clinic FK. Add a nullable scoped clinic link and allow unknown diagnosis dates, with no backfill from visit_date. All diagnoses remain peers. |
| diagnoses / diagnosis_categories | Reuse diagnosis names/code from their existing directory, including historical inactive entries; no dossier diagnosis directory. |
| visit_services / visit_procedures | Composite visit/facility FKs; actual performed_on, void markers, quantity, service/procedure directory IDs and responsible staff. Display verified stored rows. Catalog uses complete, nonvoided visits and events; do not change its eligibility/statistics. |
| visit_medications / dose_sessions / dose_session_items | Actual dispensing/administered records, medication snapshots and quantities; no generic prescription-order workflow. Show these stored medications with their source/date, without labelling them a new prescription. |
| visit_outcomes / visit_results / admissions / death_records / case_reviews | Stored results and related clinical events have specific meaning. Read visit outcomes; do not synthesize a discharge/outcome from admissions or status. No new outcome writer. |
| cancer_cases / cancer_case_diagnoses / cancer_treatments / related_people | Cancer episodes may be multiple per patient and have case diagnoses, treatment periods and legacy primary/related-person concepts. They are not a general dossier or the requested current oncology profile. Preserve them; no merge into new persistent profile and no donors field. |
| blood donors/recipients, blood_bank_people/events, blood_transfusions | Verified existing patient links (including composite visit/patient/facility safeguards). Registration is not a dossier or a visit. Keep links and event/report semantics untouched. |
| reporting_periods / reporting tables | Required for legacy visits/clinical events, optional for blood-bank events after PR #19. Dossier needs no reporting period. No change to other departments' period rules. |
| audit_logs / correction_requests / entry_drafts / patient_merges / import rows | Audit actor, facility, entity, old/new values and request UUID already exist. entry_drafts is a per-user transient payload tied optionally to a visit, not a permanent dossier. Future writers must audit dossier/profile/selection changes in the same transaction. |
| attachments / stored files | No migration provides a verified patient-visit attachment relation. export_jobs.storage_key is a generated report artifact, not a clinical attachment. Omit attachment content/endpoints; deferred. |

## Required additive foundation

- `patient_dossiers`: patient/facility FKs; manual code and complete opening_date; unique `(facility_id,patient_id)` and `(facility_id,code)`; disability_text, clinical_history, oncology indicator and current oncology scalar profile (previous examinations, medication source, conditional organization name); entered_by/updated_by FKs, lock_version, timestamps and draft/active status for the future wizard. No personal identity columns, no fixed diagnoses, no period and no invented records.
- `dossier_oncology_selections`: typed history/treatment codes as rows, unique per dossier/group/code, explicit actor/version/timestamps and dossier/facility FK. No comma-separated labels; future changes also go through existing audit_logs.
- `visits.dossier_id`: nullable composite FK to dossier `(id,facility_id,patient_id)` so a visit cannot link another patient's/facility's file; existing visits remain unassigned. Index `(dossier_id,visit_date,id)` supports actual chronology. Explicit verified migration/linking is a later authorized operation.
- `visit_diagnoses.clinic_id`: optional composite clinic/facility FK; existing unknowns stay NULL. Nullable diagnosed_on represents an unknown diagnosis date rather than fabricating one. Directory clinic deletion reference checks must include this new FK.

## Query/compatibility and rollback risks

One dossier is the outer row; correlated latest-visit/count queries and batched child queries prevent join multiplication/N+1. Latest **complete, nonvoided, nonfuture** actual visit is ordered by visit_date DESC, id DESC (same rule for count/history). Draft/voided visits are not actual completed care; opening dates do not limit recorded visits. History is independently paginated. Clinical voided/future rows are excluded; diagnosis dates may be unknown and are never replaced.

MariaDB 10.11/mysql uses InnoDB utf8mb4_unicode_ci and explicit short FK/index names. Code uniqueness follows existing facility directories, including case-insensitive collation. Add complete-date/nonblank code checks; historical dates allowed. Composite FK parent indexes must exist before adding children. DDL auto-commits: deployment needs its normal maintenance/backup procedure. No edits to historical migrations. Rollback preflights all new data/links and unknown dates before any DDL; refuses populated use rather than deleting data or fabricating values.

Substring normalized name search requires bounded facility scans (leading wildcard/REGEXP_REPLACE cannot use a name B-tree). Do not claim an index solves arbitrary substring search; inspect EXPLAIN on synthetic volume and document actual results before delivery. Pagination caps and dossier facility/date/code indexes bound work; bulk backfill/search infrastructure is not invented in this phase.

## Deferred visit/wizard behavior

No writes in Phase 1. Future full-page arrow wizard: personal data → general/oncology → diagnoses → services/procedures → medications/outcome → attachments/review. Explicit first save selects/creates patient and draft dossier (manual code + complete date required); diagnosis save creates a draft visit. Merely opening the page creates nothing. Save/continue, save draft, resume and backward navigation must use durable UUIDs, version checks, transactions and audit rows without deleting later steps. Future workflow must explicitly resolve legacy reporting-period requirements and capture diagnosis clinic/doctor independently; Phase 1 does not bypass those rules or implement draft storage endpoints. Reports, uploads and all clinical/identity mutations are deferred.
