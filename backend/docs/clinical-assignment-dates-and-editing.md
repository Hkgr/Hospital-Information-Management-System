# تواريخ الارتباط وتعديل بيانات بطاقة المريض

## السبب والنطاق

تستخدم اختيارات الطبيب في التشخيص والخدمات والإجراءات والوصفات والنتائج والتشريح المرضي علاقة `clinic_staff` بتاريخ الزيارة الفعلي. ويستخدم الممرض/الطاقم في الجرعة العلاجية العلاقة نفسها بتاريخ `given_on`، والموعد بتاريخ `planned_on`. البداية مشمولة والنهاية غير مشمولة؛ `NULL` تعني فترة مفتوحة. لا تعني نهاية الفترة تعطيل الطبيب عالميًا، ولا تعني إزالة مرشح من الخيارات حذف الطبيب من واقعة محفوظة.

فُحصت جداول العلاقات: `clinic_staff` هي العلاقة المؤرخة المستهلكة في هذه المسارات، وتشمل الأطباء والطاقم السريري المستخدم في العلاج. `staff_specialties` ليست علاقة مؤرخة؛ `staff_work_days` جدول دوام. لا يشمل التصحيح تواريخ التوظيف أو الحسابات أو الأدوار أو فترات التقارير أو الخطط والجلسات أو تواريخ الوقائع الطبية.

كانت إضافة الارتباط تبدأ من يوم الإدخال، فتختفي أسماء الأطباء عند إدخال زيارة تاريخية. وكان عرض البطاقة يمرّر صلاحيات العرض فقط لبعض لوحات العلاج، ولا يعرض روابط تعديل الأقسام المحفوظة، بينما تحديث الجرعة العلاجية متاح في API دون إجراء ظاهر في جدولها.

## تعديل الارتباطات

افتح الطبيب أو العيادة ← «تاريخ الارتباطات في المنشأة» ← «تعديل التواريخ». تاريخ الطبيب يحتاج `doctors.view` و`doctors.link`؛ تاريخ العيادة يحتاج `clinics.view` و`clinics.edit`. يشمل سجل العيادة الطاقم السريري الآخر أيضًا. لا صلاحية جديدة ولا منح تلقائي من هذا الإصلاح.

يلزم سبب، وبداية، ونهاية اختيارية. تُفحص نسختا الطبيب والعيادة تحت الأقفال بالترتيب نفسه المستخدم في الربط: الطاقم ثم العيادات ثم الفترات. تُرفض النسخة القديمة بـ409 دون كتابة، والتداخل أو البداية المكررة أو النهاية غير الصالحة بـ422. لا يعيد التصحيح فتح أو تمديد ارتباط أُغلق بأرشفة طرفه. تُسجل القيم السابقة والجديدة والفاعل في تدقيق الطرفين. تتحدث بيانات التفاصيل والاختيارات عند الحفظ أو العودة إلى تبويب البطاقة؛ تغيير العيادة أو التاريخ يلغي اختيارًا جديدًا من السياق السابق، ولا يمحو المسودة عند تحديث الخيارات فقط.

مسارات PUT المحددة الجديدة:

- `/api/doctors/{parent}/assignments/{assignment}`
- `/api/clinics/{parent}/assignments/{assignment}`

الطلب: `facility_id`, `starts_on`, `ends_on` (موجود ولو `null`), `clinic_lock_version`, `staff_lock_version`, `reason`. سجل الارتباطات يعيد النسختين اللازمتين. تحويلات Next محددة بالمعرف الرقمي، مع Sanctum والحساب النشط وقدرة `api` و`private, no-store`.

الارتباط الجديد المعتاد يبدأ افتراضيًا من `2022-01-01`. يظهر التاريخ في نموذج الطبيب والعيادة ويمكن تغييره إلى التاريخ الفعلي أو المستقبلي. يُرسل `assignment_starts_on` كما اختاره المستخدم. لا يُعاد تعيين فترة موجودة عند حفظ اسم الطبيب أو العيادة. إعادة الربط عبر API دون تاريخ صريح، بعد وجود تاريخ منتهٍ، تبدأ اليوم؛ لا تتجاوز فترة أخرى ولا تعيد فتح فترة تاريخية مغلقة ضمنيًا. إعادة فتح نفس اليوم تظل إجراء ربط صريحًا وفق السلوك السابق.

## تصحيح البدايات الموجودة — إجراء مشغّل صريح

بعد أخذ نسخة احتياطية وفق إجراء المشفى، راجع المعاينة دون تطبيق:

```bash
php artisan clinical-assignments:backdate --facility=<ACTUAL_FACILITY_ID>
```

ثم طبّق التصحيح المراجع مع مرجع تغيير حقيقي للمشغّل:

```bash
php artisan clinical-assignments:backdate --facility=<ACTUAL_FACILITY_ID> --apply --execution-reference=<CHANGE_REFERENCE>
```

حذف خيار `--facility` يفحص كل علاقات العيادات؛ المعرف الصريح غير الموجود أو صفر لا يتحول إلى كل المنشآت. لا يُفترض رقم مشفى ثابت. يعرض الأمر أعداد examined/eligible/changed/unchanged/conflicting ومعرفي الطرفين للمجموعات الملتبسة. في المعاينة changed=0 وكل مجموعة سليمة محسوبة ضمن unchanged، مع eligible كعدد مقترح مستقل.

تتحرك البداية المتأخرة عن 2022 فقط؛ الأسبق تبقى كما هي، والنهايات والمعرفات والأطراف وحالات النشاط تبقى كما هي. الفترات الملغاة ذات البداية والنهاية المتساويتين محفوظة دون إعادة فتح. البداية مفقودة غير ممكنة في المخطط الحالي (NOT NULL)، وأي بيانات غير صالحة تُعامل كتعـارض. يفحص الأمر المجموعة كاملة قبل الكتابة وتحت الأقفال؛ إذا تسببت البدايات الجديدة بتداخل أو تكرار يترك المجموعة كلها. يطبق المجموعات السليمة وحدها ويخرج بحالة فشل إن بقيت مجموعات متعارضة للمراجعة. إعادة التنفيذ لا تضيف تدقيقًا أو تغييرات للمجموعات المصححة.

## تعديل الوقائع والصلاحيات

من البطاقة أو الزيارة تظهر إجراءات تعديل التشخيصات والخدمات والإجراءات والوصفات والنتيجة والمعلومات الطبية. تفتح مساحة العمل القائمة بالقيم والمعرفات المحفوظة. العلاج يعرض تعديل الخطة والمواعيد والجرعات العلاجية وتصحيح الإعطاء والصرف، والتشريح المرضي يحتفظ بمحرره القائم. لا إعادة إنشاء للسجلات، ولا شرط للمنشئ أو عمر السجل في الكتابة السريرية المعتادة. مهلة تصحيح هوية المريض في تدفق التصحيح المحدود مستقلة ولم تُلغَ ولم تُمنح صلاحية عالمية لتغيير الهوية.

الصلاحيات المعاد استخدامها: `dossiers.medical.update`, `dossiers.visits.draft.update`, `dossiers.diagnoses.update`, `dossiers.services.update`, `dossiers.procedures.update`, `dossiers.prescriptions.update`, `dossiers.outcomes.update`, `dossiers.pathology.update`, ومع وجود `dossiers.treatment.view`: `dossiers.treatment.update`, `dossiers.treatment.schedule.update`, `dossiers.treatment.administration.correct`, `dossiers.treatment.dispensing.correct`. الوصف في محرر الدور يوضح التعديل عبر المستخدمين والزمن، مع استمرار عزل المنشأة والنسخ والتدقيق.

الزيارات المكتملة والوقائع المبـطلة ليست مسودات عادية. تبقى الكتابة عليها مرفوضة، وتوضح الصفحة ذلك وتعرض تصحيح الإعطاء/الصرف المنضبط حيث تسمح الصلاحيات والحالة. لا يوجد في التنفيذ الحالي إجراء لإعادة فتح الزيارة المكتملة؛ لا يختلق هذا الإصلاح موافقة أو إعادة فتح، ولا يمنح الحذف أو الإبطال أو الاعتماد أو الإكمال. المرفقات غير قابلة لتبديل محتواها سرًا: إضافة/تحميل/إبطال مستقل ومدقق؛ لا تُمنح صلاحية إبطالها ضمن تهيئة التعديل.

## تهيئة التعديل الأولية لمرة واحدة

```bash
php artisan patient-cards:initialize-editing
php artisan patient-cards:initialize-editing --apply --execution-reference=<CHANGE_REFERENCE>
```

الأول معاينة فقط. التطبيق الذري يستهدف الأدوار الفعالة المسندة لحسابات فعالة في مشافٍ فعالة والتي تملك أصلًا عرض التاريخ الطبي للبطاقة؛ لا يستهدف مدخل بيانات أساسي بلا وصول طبي. يحفظ متطلبات القراءة اللازمة للتعديل، ويضيف تحديث العلاج فقط للأدوار التي تملك عرضه أصلًا. سياسة المدير المحمي تعامل كاختيارات دقيقة موجودة، ولا تُوسع من اسمه أو رقم مستخدمه، وتبقى صلاحيات إدارة الوصول المحمية كما هي.

لا توجد طبقة صلاحيات مباشرة للمستخدم في التنفيذ الحالي؛ الوصول المحلي يأتي من `facility_user_roles` ثم `role_permissions`، والتفويضات العالمية من `global_user_roles`. يفحص الأمر هذه المصادر ويحافظ على التفويض العالمي المستقل. يفك صلاحيات التعديل المظلية القديمة إلى المهام الفعالة الحالية قبل إزالة تلك المنح المظلية من الأدوار المستهدفة؛ تبقى تعريفاتها وتاريخها محفوظين. هذا يمنع `dossiers.visits.update` أو `dossiers.clinical.update` من إعادة منح مهمة جزئية سحبها المسؤول لاحقًا. المنح الحالية الأخرى تحفظ، ولا تضيف التهيئة إنشاءًا أو حذفًا أو تصديرًا أو إكمالًا غير ممنوح سابقًا.

إذا كانت صلاحية لازمة معطلة/مفقودة، ترفض التهيئة التطبيق كله وتبين الدور والصلاحية؛ لا تنشّط تعريفات معطلة لتجاوز ذلك. يُحفظ إنجاز النسخة v1 كحدث append-only باسم `clinical_edit_initialization_v1` في سجل التدقيق تحت أقفال إدارة الوصول؛ إعادة الأمر بعد سحب صلاحية لا تعيدها. لا يستدعيه تشغيل التطبيق أو Seeder. لا يُحذف حدث التهيئة عند التراجع عن نسخة التطبيق أو تُجرى إعادة منح ضمن التراجع. هوية تدقيق أمر الطرفية `actor_id=NULL` مع مرجع تنفيذ صريح، وليست المستخدم 1 أو المستفيد من المنح.

## النشر والتحقق

لا تغيير مخطط ولا migration ولا Seeder مطلوب. يتطلب النشر حزمة Backend وحزمة Next مبنية من النسخة نفسها لأن التحويلات تُحسم وقت البناء. الأمران أعلاه مستقلان وصريحان: راجع معاينة الصلاحيات والتواريخ، ثم طبّق بعد موافقة المشغّل المعتادة. لا تشغّل migrate:fresh أو refresh أو reset. راجع المجموعات المتعارضة يدويًا، واختبر سجلًا تاريخيًا وصلاحية مسحوبة بحساب اختباري وفق إجراءات المشفى.

جميع نتائج PR محلية على بيانات اصطناعية وقاعدة MariaDB معزولة بعد حاجز الأمان؛ لم تُشغّل أوامر التصحيح أو التهيئة على الإنتاج. يتم توثيق نتائج المتصفح والبناء والاختبارات في وصف PR، ولا تعني أن بيانات المشفى الفعلية قد فُحصت أو صُححت.
