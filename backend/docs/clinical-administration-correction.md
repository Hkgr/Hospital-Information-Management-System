## التفعيل بالترتيب — للمشغّل، لم يُنفذ على الإنتاج

1. خذ النسخة الاحتياطية المعتادة وأوقف الكتابة أثناء نشر نسختي الواجهة والخادم المتوافقتين. راجع أي تعارضات أسماء مسبقًا؛ لا تعتمد أول تطابق.
2. من backend: `php artisan migrate:status` ثم `php artisan migrate --force` بعد مراجعة pending. إن لم تُنفذ migration الأولى، ينفذ Laravel نسختها المصححة الخاصة بالمخطط فقط ثم الترحيل الإضافي. إن نُفذت سابقًا، يتخطاها بسجلها الأصلي ويطبق الإضافي إن كان معلقًا؛ لا تعيدها ولا تسجلها يدويًا ولا تستخدم rollback لإجبار تشغيلها. لا تستخدم migrate:fresh.
3. عرّف النوعين دون تعديل تعريف معطل: `php artisan db:seed --class=ClinicalStaffTypesSeeder --force`. هذا Seeder لا يمنح صلاحيات ولا يربط أطباء. عند وجود نوع معطل يلزم قرار إداري مستقل، ولن تعيد التهيئة تفعيله.
4. حدد معرف المنشأة الحقيقي وتاريخ بدء الروابط المعتمد. إذا كانت العيادات المطلوبة موجودة بأسماء أخرى، قدّم ملف JSON محليًا عبر `--clinic-map=/private/clinics.json`: مفاتيحه `primary,blood,oncology,thalassemia,surgical,radiology` وقيمه معرفات العيادات القائمة داخل المنشأة. لا تُخمن المطابقة ولا تعيّن العيادة نفسها مرتين. المفتاح غير المعطى يُطابق الاسم الصريح، وإذا غاب يُقترح إنشاء تعريف جديد.
5. المعاينة بلا كتابة: `php artisan directory:clinical-setup --facility=FACILITY_ID --starts-on=YYYY-MM-DD`، وأضف `--clinic-map` عند الحاجة. تعرض الهوية الحالية، التغييرات، الفترات، الإضافات المقترحة، والتعارضات وبصمة `fingerprint`. راجع التقرير كاملًا، بما فيه الأثر على دليل الأطباء والإجراءات المشترك.
6. التطبيق بعد مراجعة الإدارة: الأمر نفسه مع `--apply --expect=FINGERPRINT --operator=OPERATOR_OR_CHANGE_TICKET`. يُعاد فحص المعاينة تحت الأقفال؛ تغير البيانات أو أي تعارض يمنع المعاملة كاملة. التدقيق يسجل `actor_id=null` ومرجع المشغّل، ولا ينسب التنفيذ إلى مستخدم مستفيد.
7. أعد المعاينة للتحقق، ويمكن تكرار التطبيق بالبصمة الجديدة دون تكرار أو إعادة كتابة غير لازمة. لا يلزم تشغيل seeders عامة أو تغيير الصلاحيات.
8. أعد بناء Next: `npm ci` ثم `npm run build` مع `LARAVEL_API_URL` الصحيح، وانشر standalone وأصوله بالطريقة المعتمدة. تحقق بحساب اختبار مصرح من خيارات الطبيب والحفظ والإكمال.

ما يحتاج تحديد الإدارة: معرف المنشأة، مطابقة العيادات الموجودة ذات الأسماء المختلفة، تاريخ بدء الارتباطات، حل الأسماء المتعددة، وتوزيع الاختصاصيين. العيادات الجديدة للدم والأورام والتلاسيميا والجراحة بلا افتراض داخلي/خارجي؛ يُدار مكان الرعاية من الواجهة. الروابط السابقة المغلقة تحتاج مراجعة صريحة من واجهة الإدارة ولا تُفتح آليًا.

## تصحيح مراجعة PR #64 ومسارا الترقية

### قاعدة لم تنفذ migration الأولى

نشر النسخة المصححة قبل `migrate` ضروري. أصبح `up()` في `2026_09_29_000001_add_clinical_entry_classifications.php` خاصًا بالمخطط والقيود فقط: لا إنشاء أطباء أو إجراءات، ولا تغيير أسماء المكونات، ولا اختيار نوع موظف أو أول اسم مطابق. يليها الترحيل الإضافي لتصنيف العيادات ولقطات الإجراءات. غياب أنواع RESIDENT/SPECIALIST أو وجود أسماء ملتبسة لا يمنع ترقية المخطط، ولا يبرر أي كتابة للدليل. تظل كتابة الدليل محصورة في الأمر المعتمد بعد المعاينة والموافقة.

### قاعدة نفذت migration الأولى بالفعل

يبقى سجل migrations كما هو. لا يعيد Laravel تنفيذ النسخة المعدلة، ولا نحاول محو ما كتبته النسخة القديمة أو إلغاءه تلقائيًا. تُطبق migration الإضافية إن كانت معلقة، ثم تعرض المعاينة الهويات والأنواع والروابط الحالية. بعد حل الالتباسات صراحةً، يصحح الأمر المراجع الأنواع والتصنيفات مع الحفاظ على IDs والأكواد والتراخيص والوقائع. تعديل ملف migration الأولى لا يُعد علاجًا رجعيًا لهذه البيانات؛ الأمر المراجع هو مسار تصحيحها.

في المسارين، تسلسل التفعيل هو: مراجعة الحالة → ترقية المخطط → `ClinicalStaffTypesSeeder` لتعريف الأنواع فقط → معاينة `directory:clinical-setup` → حل تعارضات الإدارة → تطبيق بالبصمة ومرجع المنفذ → معاينة تحقق. لا توجد migration جديدة إضافية لهذه المراجعة، ولا حاجة إلى تغيير الصلاحيات.

### المطابقة وتصحيح الوقائع

- يُفحص تفرّد IDs بعد حل جميع تصنيفات العيادات، سواء بخريطة صريحة أو بالاسم. المثال `primary` الصريح و`surgical` التلقائي للسجل نفسه يُرفض مع المفتاحين ومعرّف العيادة. التطبيق يعيد هذا الفحص تحت الأقفال قبل أي كتابة.
- تغيير `doctor_id` أو `manual_doctor_name` وحده لا يستدعي تصنيف الإجراء الحالي. تُحفظ لقطتا المكان والطريقة، بما فيهما القيم الفارغة القديمة، مع استمرار فحص أهلية الطبيب والمنشأة والعيادة والمكان المحفوظ.
- تغيير `catalog_id` أو `clinic_id` صراحةً في واقعة قابلة للتعديل يفحص المكان حسب الدليل الحالي، ويرفض المكان المخالف ذريًا. عند النجاح، يحفظ اللقطة الجديدة مع `lock_version` وتدقيق القديم والجديد. الوقائع المكتملة تظل خاضعة لمسار التصحيح المعتمد الحالي؛ لم يُفتح مسار كتابة يتجاوزه.
