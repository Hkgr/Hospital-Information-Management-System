# بنك الدم: الملفات ووقائع التبرع

Laravel يملك الملفات والصلاحيات والتدقيق والتبرعات. الواجهة `/blood-bank` تستخدم Sanctum Bearer بقدرة `api` والحساب الفعال واستجابات `private, no-store`. لا تغيير في FastAPI أو المصادقة أو إعدادات الإنتاج.

## التشغيل والصلاحيات

- migration: `2026_09_14_000001_add_blood_bank_registration.php` توسع `blood_donors` وتضيف `blood_recipients`, `blood_bank_screenings`, `blood_donation_codes`, `blood_bank_requests` وحقل الكود إلى `blood_donations` وتصنيف الفحص الصريح إلى `screening_tests`.
- تعاريف الصلاحيات فقط: `php artisan db:seed --class=BloodBankPermissionsSeeder` في البيئة المقصودة بواسطة مسؤول التشغيل. لا يسند هذا الأمر أدوارًا ولا يعيد تفعيل تعريف معطّل؛ ليس ضمن DatabaseSeeder ولا يمنح أي مستخدم تلقائيًا.
- أضف بالتفويض الإداري المطلوب صلاحيات `blood_bank.view/create/update` و`blood_bank.donations.create/update` إلى أدوار المنشأة في `role_permissions` واربط المستخدم بالدور عبر `facility_user_roles`.
- البحث في جميع مرضى المشفى وربط مريض جديد يحتاجان **أيضًا** `blood_bank.patients.search` من دور عالمي مسند صراحة عبر `global_user_roles`، مع create أو update في المنشأة. إسنادها إلى دور منشأة فقط لا يكفي. الاطلاع على ملف مستفيد سبق ربطه يخضع لصلاحية عرض بنك الدم.
- إضافة طبيب من النموذج تستخدم DoctorEditor وواجهة إنشاء الطبيب وربطه الحالية: `doctors.view` و`doctors.directory.create` العالمي وصلاحية الربط الحالية للمنشأة. لا تمنح صلاحيات بنك الدم إنشاء طبيب ضمنيًا.
- المنشأة هي اختيار `directoryFacility`: قيمة `facility_id` الصريحة في الرابط، وإلا أول منشأة مسموحة في ترتيب `/api/user` مع `blood_bank.view`. لا انتقال صامت من منشأة مرفوضة، ولا متغير بيئة أو رمز أو رقم مشفى ثابت. يعرض القسم اسم المشفى دون قائمة منشآت إضافية.
- طرق HCV/HIV/HBsAg تأتي من `screening_tests` بعد تحديد `blood_bank_analyte` صراحة بواسطة مسؤول الدليل اعتمادًا على التصنيف المعتمد. القيم المسموحة `HBsAg`, `HCV`, `HIV` أو null؛ لا تصنيف من الاسم ولا بيانات مختبر مخمّنة. عدم وجود تصنيف يبقي الطريقة غير معروفة.

## الملفات

كود دائم من معرّف الملف: `BD-00000001` للمتبرع، `BR-00000001` للمستفيد؛ الأصفار حد أدنى ولا تُقتطع المعرفات الكبيرة. أكواد المتبرعين التاريخية تبقى كما هي. لا تُقسّم الأسماء التاريخية آليًا؛ عند استكمال بيانات ملف قديم يُدخل المستخدم الاسم الأول والعائلة صراحة.

المتبرع مستقل دون patient أو visit جديد. المستفيد إما `person_mode=direct` ببيانات شخصية، أو `person_mode=patient` مع `patient_id` فقط دون الحقول الشخصية. قيد قاعدة البيانات يمنع خلط المسارين؛ عنوان المريض يُقرأ من الأصل ولا ينسخ. جهة المستفيد حقل مستقل عن عنوان السكن. يمنع unique(facility_id, patient_id) تسجيل الملف المرتبط مرتين. تشابه الأسماء لا يدمج أشخاصًا؛ أعد استخدام الملف المباشر باختياره من القائمة صراحة.

الاسم الأول والعائلة مطلوبان للإدخال المباشر. الحقول الأخرى الشخصية تستخدم نفس أدلة المحافظة والمدينة ودقة الميلاد والجنس وحالة النزوح في المخطط. الزمرة والمكون يمكن أن يبقيا غير معروفين. العلاقة الجديدة أو المتغيرة تتطلب عيادة فعالة وطبيبًا حاليًا مؤهلًا مرتبطًا بها داخل المنشأة؛ تُقفل أطراف العلاقة بالترتيب المستخدم في الأطباء والعيادات. المسؤولية التاريخية غير المتغيرة تبقى محفوظة، وتمنع مراجع بنك الدم حذف الطبيب أو العيادة نهائيًا.

فحوص الملف مستقلة تمامًا عن `blood_donation_screenings`: لكل analyte حالة ونتيجة منفصلتان. `complete` يحتاج نتيجة `negative/positive/indeterminate`، وكل حالة أخرى تحتاج null. لا يُفسر غياب النتيجة كسلبية ولا يُستنتج قبول التبرع.

## وقائع التبرع

إنشاء الملف لا ينشئ تبرعًا أو نقل دم أو زيارة. «تسجيل تبرع» في ملف المتبرع ينشئ واقعة فعلية في `blood_donations` بحالة `pending`؛ التاريخ وABO وRh وعدد الوحدات الموجب (حتى أربع منازل عشرية) مطلوبون ولا تُنسخ نتائج الملف.

`DON-YYYYMMDD-ID` يستخدم `donated_on` الفعلي ومعرّف التبرع العام بأصفار إلى ست خانات على الأقل. لا إعادة عد يومية؛ يمكن للشخص نفسه عدة تبرعات في اليوم. المستقبل مرفوض حسب توقيت المنشأة. يلزم وجود **فترة تقارير مفتوحة واحدة** تغطي التاريخ؛ لا ينشئ القسم فترة. التصحيح يتطلب بقاء الفترة السابقة مفتوحة أيضًا. لا يعدّل إلا التبرع pending غير الملغى.

تصحيح التاريخ يحدّث الكود ويحفظ الكود السابق في السجل الفريد للأسماء البديلة داخل المعاملة نفسها، ويسجّل القيم القديمة والجديدة في التدقيق. إعادة التاريخ إلى قيمة سابقة تعيد الكود الخاص بالواقعة نفسها. البحث بأي كود سابق يعيد الواقعة الحالية مرة واحدة. migration تولّد الأكواد التاريخية من تاريخ كل تبرع ومعرّفه دون تعديل البيانات العلاجية أو updated_at.

## العقد والمسارات

كل طلب يحمل `facility_id` وBearer. التوثيق التفاعلي ضمن `/docs/api` والمخطط `/docs/api.json` وفق سياسة إتاحة التوثيق الحالية.

| المسار بعد `/api/blood-bank` | الطرق | الغرض |
| --- | --- | --- |
| فارغ | GET / POST | قائمة الملفات / إنشاء ملف |
| `/{kind}/{item}` | GET / PUT | عرض/تعديل donor أو recipient |
| `/options` | GET | المنشأة والصلاحيات والمكونات والفحوص والمحافظات |
| `/cities` | GET | مدن governorate_id |
| `/clinics` | GET | عيادات المنشأة المتاحة |
| `/doctors` | GET | أطباء clinic_id الحاليون |
| `/patients`, `/patients/{patient}` | GET | البحث العالمي المصرّح / بيانات الربط |
| `/donor/{donor}/donations` | GET / POST | قائمة التبرعات / تسجيل واقعة |
| `/donor/{donor}/donations/{donation}` | GET / PUT | عرض / تصحيح الواقعة |

معرفات المسارات رقمية وتحويلات Next محددة تحت `/hospital-api`؛ لا تحويل عام. القوائم تعيد `{data: [], meta: {page, per_page, total, last_page}}`؛ الملف يعيد `{data: profile}` مع capabilities عند القراءة. الفحوص تظهر كقائمة داخل الملف؛ التبرعات لها جدول ومسارات منفصلة. البحث بالاسم الكامل والكود خادمي قبل الترقيم، مع تطبيع المسافات ومعاملة `%` و`_` حرفيًا. خيارات الصفحات 10/20/50/100؛ جداول الخيارات الطبية 20 لكل صفحة.

POST/PUT يتطلبان UUID `request_id` محفوظًا لكل مستخدم ومنشأة. إعادة المحتوى نفسه لا تُنشئ سجلًا ثانيًا؛ إعادة المفتاح بمحتوى مختلف 409. PUT يتطلب `lock_version`؛ تعارض النسخة 409 ولا يُدمج تلقائيًا. الواجهة تحتفظ بالمسودة وتتيح جلب الأحدث، ثم اختيار الحقول المطلوب تطبيقها صراحة وإعادة الحفظ. تجميع الحالة/النتيجة/الطريقة لكل فحص يحافظ على معناها عند المراجعة.

الأخطاء: 401 دون مصادقة، 403 للصلاحية/المنشأة/الحساب/القدرة، 404 للسجل غير المتاح، 409 للتعارض/تكرار ملف المريض/حالة التبرع، 422 لحقول أو علاقة أو فترة غير صالحة، 500 بعقد `BLOOD_BANK_UNAVAILABLE` دون تفاصيل داخلية. أخطاء الحقول تبقى بصيغة Laravel JSON.

## تحقق محلي آمن

استخدم `.env.testing` مع MySQL معزولة واسم اختباري ومضيف loopback أو تصريح العزل المعتمد. لا SQLite ولا اتصال بالإنتاج. ابدأ بـ:

```sh
php artisan test-db:check --connect --env=testing
php artisan test --env=testing --filter='BloodBankTest|ClinicApiTest|DoctorApiTest|DirectoryLifecycleTest'
```

لا تشغّل RefreshDatabase بالتزامن مع بيانات اختبار حي. بعد انتهاء Feature Tests: ابن Next standalone باستخدام `LARAVEL_API_URL=http://127.0.0.1:8015/api`، وانسخ public و.next/static وفق طريقة Next المعتمدة، وشغّله على loopback:3105. خادم الاختبار الحقيقي:

```sh
php -S 127.0.0.1:8015 tests/Support/blood-bank-server.php
```

من frontend: `node --test tests/blood-bank-live.test.mjs`. الاختبار يجهز بيانات اصطناعية عبر حاجز MySQL، ويرسل عبر Next فقط، ويعيد قراءة النتائج ويتحقق من عدم تغير أعداد الوقائع الطبية، ثم يلغي توكناته. سجلاته وتوكناته تبقى في storage/framework/testing المتجاهل؛ لا ترفعها. اللقطات المحلية داخل `.superdesign/blood-bank-review` بأحجام 390/768/1440. اختبارات الأعطال المعلّمة صراحة تحقن فشل/تأخير الشبكة فقط ولا تستبدل التحقق الحقيقي.

الخارج عن النطاق: قبول/رفض التبرع، نتائج فحوص التبرع الفعلي، مخزون المكونات، نقل الدم، استنتاج أهلية طبية، وصلاحيات/نشر الإنتاج.
