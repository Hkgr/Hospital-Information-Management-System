# إدارة الوصول الصريح وتوحيد المدير

## السلوك المعتمد

`super_admin` هو الدور الإداري المحمي المعتمد. الإسناد العالمي لدور محمي فعال مع حساب فعال هو أساس التفويض، وليس رقم المستخدم أو اسمه. المستخدم 1 هو هدف أمر التوحيد فقط؛ لا ينشئه الأمر ولا يغيّر أيًا من بيانات حسابه.

يُحوّل الوصول الكامل السابق مرة واحدة إلى صفوف فعلية في `role_permissions`: جميع التعريفات الفعالة لحظة المعاينة، واتحاد تعريفات الدورين القديمة دون حذف التعريفات المعطلة. بعد ذلك لا يُضاف أي تعريف مستقبلي تلقائيًا. لا توسّع الصلاحيات القديمة العامة ولا الأدوار الإضافية سياسة المدير المحفوظة، ولذلك إزالة `clinics.edit` تمنعها حتى مع بقاء `clinics.update` أو دور آخر يمنحها.

الأدوار العادية تحتفظ بتوافق الصلاحيات السابقة أحادي الاتجاه. لا يُختزل دور مدخل البيانات ولا تُسحب تعييناته عند الترقية. يختار المسؤول التغيير بعد معاينة فرق الوصول.

يبقى المدير قادرًا على الوصول إلى المنشآت الفعالة وفق السياسة المحفوظة؛ إنشاء منشأة لا يضيف صلاحيات جديدة. الحد الأدنى المحمي: `users.view`, `roles.view`, `roles.update`, `roles.delegate`, `users.global.view`, `users.global.manage`, `users.roles.assign`. يُعرض سبب الحماية في المحرر. لا يمكن تعطيل الدور أو إسناده أو سحب حسابه من واجهات الحسابات المعتادة. جميعها ترفض أيضًا تعديل الحساب الحالي لنفسه. لا يتيح اسم مشابه أو صلاحية جزئية تعديل الدور المحمي.

`roles.delegate` تفويض عالمي لإدارة الإسناد، منفصل عن تنفيذ الأعمال الطبية، ويحتاج أيضًا دورًا نظاميًا محميًا؛ لا يوزّعه محرر التفويض التشغيلي على حساب عادي. يظل `roles.view` شرط العرض و`roles.update` شرط التعديل. حساب العرض فقط يستطيع فتح `/users` وتفاصيل الدور دون `users.view`، لكنه لا يرى بيانات الحسابات.

## المسارات والعقود

جميع المسارات تحت `/api/users` وداخل middleware المصادقة الفعلية والحساب الفعال وقدرة `api` والخمول، وتبقى الاستجابات خاصة غير قابلة للتخزين.

| المسار | التفويض |
| --- | --- |
| `GET roles`, `GET roles/{role}`, `GET roles/options` | `roles.view` داخل المشفى |
| `POST roles` | `roles.view` و`roles.create` وصلاحيات قابلة للتفويض |
| `PUT roles/{role}` | `roles.view` و`roles.update`؛ دور غير محمي وصلاحيات قابلة للتفويض |
| `PUT roles/{role}/protected-permissions` | الدور المحمي + `roles.delegate` عالميًا + عرض/تعديل الأدوار محليًا |
| `GET {user}/access` | `users.view`؛ تفاصيل التفويض العالمي تحتاج `users.global.view` عالميًا |
| `PUT {user}/access` | `users.roles.assign` لتغيير المحلي؛ `users.global.manage` و`roles.delegate` العالميان مع الدور المحمي لتغيير العالمي |

تعديل الدور يحتاج `facility_id`, `name_ar`, `permission_ids`, `lock_version`, `reason`. اسم الدور المحمي ثابت؛ المسار يغيّر صلاحياته فقط. تعديل وصول الحساب يحتاج `facility_id`, `lock_version`, `reason` وإحدى `local_role_ids` أو `global_permission_ids`. إغفال أحد القسمين يحفظه كما هو. `global_permission_ids: []` سحب صريح للتفويض العالمي. لا تمنح قراءة الخيارات أو إنشاء الحساب تفويضًا عالميًا.

النسخة المحلية للحساب هي `users.lock_version` الحالية، المشتركة مع إدارة حسابات التسجيل؛ لا توجد ساعة نسخ موازية تسمح بتجاوز تعديل سابق. تحفظ الكتابة تحت أقفال الحساب والأدوار مع إعادة التفويض، ويرفض التعارض بـ409. الصلاحيات المعطلة والأدوار المعطلة لا تُعاد تهيئتها.

التفويض العالمي التشغيلي يُحفظ في دور داخلي دقيق `delegation-{user id}` مربوط عالميًا بالحساب وحده؛ لا يمكن إسناده محليًا أو تحريره من إدارة الأدوار العامة. الحفظ العالمي **استبدال صريح** للتعيينات العالمية السابقة، يسبقه عرض القيم الفعالة والفرق، ويحفظ التدقيق مراجعها وصلاحياتها السابقة. لا ينقل الدور المحلي كله عالميًا. إلغاء اختيار صلاحية في هذا الدور لا تعيده توسعة قديمة.

## الترحيل والمعاينة — أوامر للمشغّل، لم تُنفّذ على المشفى

الترحيل الإضافي: `2026_10_01_000001_add_explicit_access_administration.php`. يضيف `roles.lock_version` و`roles.access_consolidated_at` ويعرّف أربع صلاحيات بإدراج يتجاهل الموجود (`AccessAdministrationPermissionsSeeder`) دون إسنادها لأي حساب ودون إعادة تفعيل تعريف معطل. لا تمس هذه الخطوة الجداول الطبية. لا تشغّل seeders عامة.

خطط لنافذة صيانة: بين نشر سياسة التفويض الصريحة وإتمام التوحيد قد يملك المدير القديم صفوف صلاحيات أقل من وصوله التلقائي السابق. لا تفتح التطبيق قبل التحقق من التوحيد. لا يُنفّذ الأمر تلقائيًا ضمن migration؛ يجب مراجعة المعاينة أولًا.

مثال Bash للمشغّل، بقيم الاتصال المعتمدة محليًا لديه ودون أسرار في المستودع:

```bash
# قبل نافذة الصيانة: نسخة احتياطية كاملة محفوظة خارج public والمستودع.
umask 077
mysqldump --login-path=his-operator --single-transaction --routines --triggers --events "$HIS_DATABASE" > "$BACKUP_FILE"
# تحقّق من النسخة باستعادتها في بيئة معزولة، لا فوق قاعدة مأهولة.

cd backend
php artisan down
# تثبيت الإصدار وcomposer وفق إجراء النشر المعتمد.
php artisan migrate --force
php artisan access:consolidate-admin > /secure/review/access-preview.json
```

تحتوي المعاينة تعريف الدورين، وصلاحياتهما وتعييناتهما المحلية والعالمية، والمنشآت الفعالة، والفرق وبصمة الحالة. ترفض غياب/تعطيل المستخدم 1، أو غياب/تعطيل المدير، أو تعطيل حد إدارة الوصول، أو وجود **أي مستخدم آخر** مسند إليه أحد الدورين. عدم وجود الدور القديم مسموح؛ لا يُختلق. الأرقام والأسماء الفعلية تُقرأ من القاعدة ولا تُثبّت من المثال المرسل.

بعد مراجعة الملف والنسخة الاحتياطية فقط:

```bash
php artisan access:consolidate-admin --apply \
  --fingerprint="البصمة_من_المعاينة" \
  --execution-reference="مرجع_تذكرة_التغيير_والمشغل" \
  --reason="سبب_التوحيد_المراجع"
php artisan access:super-admin
php artisan access:consolidate-admin > /secure/review/access-after.json
```

يُعاد بناء المعاينة تحت القفل قبل أي كتابة؛ البصمة القديمة أو التعارض يرفضان التنفيذ كاملًا. يُؤرشف `full_access_user_1` بتعطيله، مع إبقاء صف الدور وصلاحياته وتعييناته التاريخية. تُضاف تعيينات `super_admin` اللازمة دون تكرار؛ الحساب نفسه لا يتغيّر. التدقيق يربط التعيينات القديمة والهدف بمرجع المشغّل وبصمة المعاينة، و`actor_id` فارغ لأمر الطرفية، لا رقم المستفيد. إعادة التشغيل بمعاينة حديثة لا تعيد منح صلاحيات ألغاها المسؤول لاحقًا ولا تكرر التدقيق.

`access:super-admin --apply` القديم يرفض المنح ويوجّه إلى الأمر المراجع. `doctors:grant-access` يرفض المدير المحمي والدور المؤرشف والأدوار العالمية الداخلية؛ لا يصلح وسيلة لإعادة الصلاحيات المستثناة.

إعادة بناء Next إلزامية للمسارات الصريحة الجديدة:

```bash
cd ../frontend
npm ci
# اضبط LARAVEL_API_URL المعتمد في بيئة البناء؛ لا تطبّق عنوان الاختبار المحلي.
npm run build
# شغّل حزمة standalone الجديدة مع public و.next/static وفق إجراء النشر.
cd ../backend
php artisan up
```

تحقق من تفاصيل المدير والاختيارات الفعلية، ومن تسجيل فرق وصول اصطناعي بحساب اختبار مخوّل. لا تعتمد على عدد ثابت للصلاحيات. لا تغير فترة الخمول ولا تعتبر طلبات الخيارات نشاطًا لتجديد الجلسة.

## التراجع وحفظ البيانات

لا تستخدم `migrate:fresh`, `migrate:refresh`, `db:wipe` أو استعادة نسخة فوق قاعدة مأهولة. `down()` يرفض إسقاط النسخ وسجل القرار؛ لا يحذف أدوارًا أو تعيينات أو تدقيقًا ولا يختلق بيانات لاستعادة قيد قديم.

قبل أي اختيارات إدارية جديدة، يمكن للمشغّل إيقاف التطبيق (`php artisan down`) وإعادة حزمة التطبيق السابقة المعتمدة وإعادة بنائها، مع إبقاء المخطط الإضافي والنسخ الاحتياطية والتدقيق. **بعد سحب صلاحيات تشغيلية لا ترجع إلى كود المنح التلقائي القديم** لأنه سيبطل الاستثناءات؛ استخدم إصلاحًا أماميًا أو استعد الاختيارات المراجعة عبر محرر الدور مع السبب والنسخة. عند تعذر ذلك يبقى التطبيق في الصيانة لمراجعة استرجاع الوصول من المعاينة والتدقيق؛ لا توجد استعادة آلية تكتب فوق قرارات أحدث.

## دليل إعداد موظف التسجيل

مدير النظام ← الأدوار ← تفاصيل مدخل البيانات ← تعديل الصلاحيات ← معاينة مجموعة «التسجيل والبيانات الأساسية» ← مراجعة الفرق والسبب ← تفاصيل الحساب ← إسناد الدور داخل المشفى ← اختيار البحث المحدود وإنشاء الهوية عالميًا ← معاينة الفرق والتأكيد.

الحقول الستة ظاهرة بعناوين عربية ونطاقها. لا تمنح هذه المجموعة التاريخ الطبي أو التصدير أو الحذف؛ تظل تلك مهام مستقلة. البحث يعرض الحد التعريفي فقط، والحفظ يعيد استعمال المعاملات ومنع التكرار وكود البطاقة الحالي. يُحدّث الوصول في الخادم بكل طلب، بما فيه سحب التفويض وتعطيل الحساب/الدور/الصلاحية.

المثال المصوّر داخل `/guide`، ولقطات التنفيذ ونتائج التشغيل في [مراجعة الواجهة](../../frontend/docs/explicit-access-review.md).
