# مدخل البيانات: إدخال البطاقة دون إنشاء الأدلة

## العقد الحالي

دور `data_entry` المحلي يتيح تسجيل المريض وبطاقته وزيارته الأولى من «بطاقات المرضى»، ثم عرض وحفظ واستكمال الأقسام الطبية ضمن المشفى المصرح به. اختيار تعريف موجود وإضافته إلى واقعة المريض يختلف عن إنشاء تعريف في الدليل. يستمر التحقق من التاريخ والأهلية والعلاقات والنسخ وUUID وحالة الزيارة؛ لا تعيد الصلاحيات فتح زيارة مكتملة أو واقعة مبطلة.

الملف `admin_his12-10.sql` استُخدم مرجعًا لقراءة دور مدخل البيانات وصلاحياته فقط، دون استيراد أو اتصال بقاعدة المشفى. يحتوي الدور فيه على صلاحيات إنشاء الأدلة الخمس، بينما يفتقد `dossiers.attachments.download`. تختلف الفروق الفعلية بحسب القاعدة؛ معاينة الأمر أدناه هي المرجع قبل التطبيق.

## صلاحيات تعريف الدور الافتراضي

| المهمة | الصلاحيات |
| --- | --- |
| تسجيل البطاقة والبيانات الأساسية | `patients.basic.view`, `patient_cards.register`, `patients.own.correct`, `patients.corrections.request` |
| قراءة البطاقة والزيارات وتسجيلها | `dossiers.medical.view`, `dossiers.visits.view`, `dossiers.create`, `dossiers.personal.update`, `dossiers.medical.update`, `dossiers.visits.create`, `dossiers.visits.draft.update` |
| الوقائع الطبية | `dossiers.diagnoses.update`, `dossiers.services.update`, `dossiers.procedures.update`, `dossiers.prescriptions.update`, `dossiers.outcomes.update` |
| الصور والمرفقات | `dossiers.attachments.view`, `dossiers.attachments.upload`, `dossiers.attachments.download` |
| المراجعة والإكمال | `dossiers.finalize`, `dossiers.visits.complete` |
| التقييم والتشريح المرضي | `dossiers.assessment.update`, `dossiers.pathology.create`, `dossiers.pathology.update` |
| العلاج ومواعيده ووقائعه | `dossiers.treatment.view`, `dossiers.treatment.create`, `dossiers.treatment.update`, `dossiers.treatment.schedule.create`, `dossiers.treatment.schedule.update`, `dossiers.treatment.administer`, `dossiers.treatment.dispense`, `dossiers.treatment.administration.correct`, `dossiers.treatment.dispensing.correct` |
| عرض الأدلة الموجودة | `clinics.view`, `doctors.view`, `catalog.view` |

التعريف الافتراضي لا يمنح الحذف أو التصدير أو إدارة الحسابات والأدوار أو استثناء تحقق العلاج أو إبطال الوقائع. تسجيل بيانات الهوية يتم ضمن معاملة البطاقة المحلية الحالية؛ لا يُمنح تفويض عالمي جديد للبحث أو إنشاء أو تغيير هوية المرضى. تعديل الهوية المشتركة المحفوظة يبقى وفق التصحيح المحدود والمراجعة القائمة؛ `dossiers.personal.update` وحدها لا تتجاوز تفويض تغيير الهوية. لا يتغير نطاق الحقول أو المهلة أو حماية الهوية المشتركة.

## الصلاحيات المسحوبة من الدور

- `clinics.create`
- `doctors.directory.create`
- `catalog.directory.create`؛ وتشمل إنشاء فئات الدليل أيضًا.
- `diagnoses.create`
- `medications.create`؛ تشمل صفحة الأدوية والإضافة السريعة.
- `stock.suppliers.write`, `stock.stores.write`, `stock.suppliers.manage` إذا كانت مسندة؛ يمنع سحب المتطلب التاريخي إعادة تفعيل إنشاء تعريف المورد/المستودع عبر الصلاحيات المظلية.

ليست `patients.create` تعريف دواء/تشخيص، وليست `dossiers.treatment.create` إنشاء دليل؛ لذلك لا تُعامل كصلاحية إنشاء دليل سريري. لم يُضف الأمر تفويضًا عالميًا لأي منهما. فُحصت جميع مسارات إنشاء التعريفات الحالية: العيادات والأطباء والخدمات والإجراءات والأدوية والفئات والتشخيصات والموردون والمستودعات. لا توجد صلاحية إضافية لإنشاء التشخيص من صفحة مستقلة تتجاوز المسار المحمي.

تتحكم الواجهة الحالية في الأزرار بالقدرات/الصلاحيات، ويتحقق Laravel من الطلب المباشر. لا يوجد شرط في المصادقة أو الواجهة يعتمد على اسم `data_entry`. من يملك دورًا آخر مخولًا بالإضافة يبقى مخولًا وفق اتحاد أدواره؛ الاختبار الأساسي لحساب يملك `data_entry` وحده.

## تفعيل قاعدة منشورة

لا migration ولا تغيير مخطط ولا استيراد SQL. انشر Backend من النسخة المراجعة ثم راجع المعاينة:

```bash
php artisan access:data-entry-card-permissions
```

تعرض ADD وREMOVE وDEFINE MISSING دون كتابة تعريفات أو منح أو نسخ أو تدقيق. ثم نفّذ إجراء المشغّل المراجع، مستبدلًا المعرف والمرجع بقيم حقيقية:

```bash
php artisan access:data-entry-card-permissions --apply --facility=<ACTUAL_FACILITY_ID> --execution-reference=<CHANGE_REFERENCE_AND_OPERATOR>
```

`--facility` هو المشفى الذي يسجل فيه تدقيق الإجراء، **ولا يحصر تعديل الدور المشترك في بعض إسناداته**. يتأثر كل من يملك الدور الحالي ضمن نطاق إسناداته الموجودة. لا تُضاف إسنادات محلية أو عالمية، ولا تُغيّر الأدوار الأخرى أو المستخدمون أو حالة نشاط الدور أو التعريفات أو البيانات الطبية.

يلزم دور `data_entry` موجود وفعال وغير محمي، ومشفى فعال، ومرجع تنفيذ. إذا غاب الدور أو كان معطلًا أو محميًا، أو كانت صلاحية مطلوبة معطلة، يفشل التطبيق قبل الكتابة. تُعرّف الرموز المطلوبة المفقودة فقط بأسمائها المعتمدة، دون إعادة تنشيط تعريف معطل. الأقفال تتبع إدارة الوصول الحالية، وتُحدّث نسخة الدور عند تغير المنح، ويُسجل السابق والجديد والإضافات والمسحوبات ومرجع المشغّل؛ `actor_id=NULL` لأمر الطرفية، ولا يُنسب التنفيذ للمستخدم 1.

إعادة الأمر على الحالة المطابقة لا تضيف منحًا أو تدقيقًا ولا تغيّر النسخة. التطبيق الصريح يعيد مطابقة متطلبات هذا الدور إذا عدّلها المسؤول لاحقًا؛ لذلك راجع معاينته قبل كل تطبيق. لا يستدعيه بدء التطبيق أو DatabaseSeeder. `PermissionMatrixPhaseOneSeeder` يستخدم التعريف الجديد عند إنشاء الدور لأول مرة فقط، ويحفظ اختيارات الدور الموجود عند إعادة seeding، ومنها الصلاحيات التي سحبها المسؤول. لا تستخدم Seeder عام لتفعيل هذا التصحيح على القاعدة المنشورة.

الأمر إضافي فيما يخص صلاحيات البطاقة، ومحدد فيما يسحبه من إنشاء الأدلة؛ يحفظ بقية المنح التاريخية الصريحة للدور الموجود ولا ينفذ تضييقًا إداريًا عامًا خارج المهمة. راجعها من محرر الدور إذا أراد المشفى تعديلها مستقبلًا.

بعد التطبيق، أعد فتح الواجهة أو تحديث الصفحة لتحديث القدرات، ثم تحقق بحساب مدخل بيانات فقط: رابط تسجيل البطاقة من قائمتها، استكمال الأقسام، اختيار تعريفات موجودة، غياب إنشاء الأدلة، و403 للإنشاء المباشر. صلاحيات الخادم ديناميكية وتنعكس على الرموز الحالية دون إصدار رمز بصلاحيات مخزنة داخله.

## التحقق المحلي

اختبارات Laravel تستخدم قاعدة MariaDB اختبارية قائمة ومعزولة بعد `test-db:check --connect --env=testing`، مع runner حفظ القاعدة دون migrations أو refresh. تشمل كل أقسام الإدخال والتقييم والعلاج والمرفقات والمراجعة والإكمال، وUUID، ودورة حياة الزيارة، وعزل المشفى، والمنع المباشر دون كتابة، والمستخدم المخول، والمعاينة والتطبيق وإعادة التنفيذ والتدقيق وحماية الدور المحمي والتعريفات المعطلة. تغطي اختبارات المتصفح تدفقًا حقيقيًا عبر Next standalone وLaravel وMariaDB، دون page.route أو استجابات API محاكية. تُوثق نتائج التشغيل الفعلية في PR؛ لا تعني تنفيذًا أو تحققًا على قاعدة المشفى.
