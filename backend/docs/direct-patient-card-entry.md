# إضافة بطاقة المريض مباشرة

## الاستخدام والصلاحيات

من «بطاقات المرضى ← إضافة بطاقة مريض» تظهر حقول المريض فورًا في `/patient-cards/new`. البحث عن شخص موجود اختياري داخل النموذج، وفحص الأسماء المشابهة يعمل أثناء الإدخال. راجع التشابه صراحة؛ الاسم المتشابه لا يدمج الأشخاص. اختر الهوية المؤكدة أو افتح بطاقتها القائمة بدل إنشاء نسخة. تاريخ فتح البطاقة وتاريخ الزيارة الفعلي مطلوبان، ولا يُفترض تاريخ زيارة أو بيانات طبية.

الدور المحلي الذي يملك `patients.basic.view` و`patient_cards.register` يستطيع إضافة الهوية والبطاقة والزيارة الأولى في معاملة واحدة، دون تفويض عالمي منفصل أو دور باسم استقبال. البحث المحلي يعيد عشر هويات كحد أقصى لها بطاقة أو زيارة في المشفى، أو هوية أنشأها الموظف ولم ترتبط بعد بسياق آخر. لا يعطي التاريخ الطبي أو التشخيصات أو العلاج أو المرفقات. الهوية خارج هذا النطاق تحتاج موظفًا مخولًا بمطابقة الدليل المشترك، ولا يجوز إنشاء نسخة بديلة لتجاوز المنع. التفويض العالمي الصريح `patients.basic.search` ما زال يتيح البحث التعريفي الأوسع؛ لا تمنحه سياسة البطاقة تلقائيًا.

الحفظ يعيد استخدام `DossierPersonalWriter` وحجز الكود ودفتر UUID والتدقيق ونافذة التصحيح الحالية. إعادة إرسال الطلب نفسه تستعيد البطاقة والزيارة نفسيهما؛ تغيير محتواه مع UUID نفسه مرفوض. لا يُنشئ فتح النموذج سجلًا. تعاد مراجعة الصلاحية والسياق داخل الحفظ؛ استعمال معرّف مريض خارج النطاق مرفوض. لا تمنح صلاحية الإضافة تعديل الهوية القائمة أو الحذف أو التصدير أو العمل الطبي. استكمال المسودة والزيارات اللاحقة يستخدمان سير العمل الطبي وصلاحياته القائمة.

من محرر الدور اختر «بطاقات المرضى والبيانات الأساسية»، وراجع الإضافات قبل الحفظ. القالب لا يتضمن تفويضات الدليل العالمي؛ لا تُنسخ الأدوار المحلية إلى `global_user_roles`. لا تُعدّل هذه المعالجة التعيينات القائمة أو اختيارات المدير الشامل.

## المراجعات والتوافق

- التصحيحات ومراجعة التكرار ضمن `/patient-cards/reviews` بصلاحيات المراجعة الحالية، والموافقة على الهوية المشتركة ما زالت تحتاج تفويضها العالمي المستقل. الطلبات والتدقيق التاريخيان محفوظان.
- الحسابات والأدوار والتفويضات من `/users` فقط. `GET /api/reception/reviews/accounts` و`PUT /api/reception/reviews/accounts/{user}` يعيدان `410 RECEPTION_ACCOUNTS_RETIRED` دون تغيير حساب أو رمز أو إسناد، حتى للمخول سابقًا.
- `/reception` رابط توافق إلى البطاقات؛ `/reception-admin` يحول إلى مراجعات البطاقات، أو `/users` لتبويب الحسابات القديم. لا يوجد نموذج استقبال ثانٍ أو قسم مستقل في التنقل والدليل.
- المسارات الأساسية والمراجعات تحت `/api/patient-cards`، وتستخدم الـControllers والسياسات نفسها التي تخدم أسماء `/api/reception` التاريخية. تبقى الأخيرة للتوافق، عدا إدارة الحسابات المعطلة. تحويلات Next محددة، ومعرّفات التفاصيل رقمية.
- تدقيق فتح البطاقة عبر المسار الجديد يستخدم `surface=patient_card`؛ أحداث `reception` القديمة لا تتغير. التفويض والعثور على السجل يسبقان تسجيل الفتح.

## النشر والتحقق

**لا migration ولا Seeder ولا SQL لتحديث بيانات المشفى في هذا الإصلاح.** لا حاجة إلى إعادة تهيئة أو ترحيل قاعدة مأهولة. انشر الخادم والواجهة معًا بإجراءات المشغّل المعتادة؛ أعد بناء Next مع عنوان Laravel الصحيح لأن التحويلات تُحسم أثناء البناء:

```bash
cd frontend
npm ci
LARAVEL_API_URL=https://internal-laravel.example/api npm run build
```

العنوان أعلاه مثال فقط. انسخ `public` و`.next/static` إلى حزمة standalone وفق إعداد النشر القائم وأعد تشغيل خدمتها؛ لا يتطلب ذلك تعديل بيانات الإنتاج. امسح/أعد بناء كاش مسارات Laravel وفق إجراء النشر القائم حتى تظهر `/api/patient-cards`.

اختبر بحساب محدود الصلاحيات وحساب طبي مخول: الإضافة، استعادة الحفظ بنفس UUID، فتح المسودة، الاستكمال، رفض البيانات الطبية والتصدير والحذف للحساب المحدود، ومراجعة الطلبات القديمة. لا تستخدم قاعدة المشفى لهذه الاختبارات. على قاعدة اختبار موجودة مكتملة المخطط، يشغّل bootstrap التالي المعاملات دون migrations أو refresh:

```bash
php artisan test-db:check --connect --env=testing
php artisan test --env=testing --bootstrap=tests/Support/preserve-database.php --filter='DirectPatientCardTest|PermissionMatrixTest|TaskPermissionsTest|ReceptionReviewTest|ExplicitAccessAdministrationTest'
```

اختبارات المتصفح الفعلية: `direct-card-entry-live.test.mjs` و`unified-registration-live.test.mjs` و`explicit-access-live.test.mjs` و`reception-live.test.mjs` و`reception-review-live.test.mjs`. تستخدم Next standalone → Laravel → MariaDB المعزولة دون اعتراض API. تهيئة الاختبار تضيف بيانات اصطناعية فقط، وتعطّل حساباتها عند الانتهاء مع حفظ تاريخها؛ لا تمحو البيانات القائمة. نتائج التشغيل الفعلية موثقة في PR.
